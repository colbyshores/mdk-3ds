1. F1 (Critical) — CONFIRMED, FIXED.
--------------------------------------------------------------------------------
`vk_context.cpp`'s `endFrame` did:

    vkCmdEndRenderPass(frame.commandBuffer);
    ... VkSubmitInfo::pCommandBuffers = &frame.commandBuffer ...
    vkQueueSubmit(...)

and nothing, anywhere in the tree, ever called `vkEndCommandBuffer` on that
buffer. `grep -rn "EndCommandBuffer" mdk_linux/src/` before this batch returned
two hits, both in `renderer_vk.cpp`'s ONE-SHOT path (a comment at :342 and the
call at :353). Zero in the file that owns the frame.

A command buffer that was begun and never ended is in the RECORDING state, and
`VkSubmitInfo::pCommandBuffers` may only name a pending or executable one
(VUID-vkSubmitInfo-pCommandBuffers-00075). So every frame this backend has ever
presented was submitted in an invalid state. Lavapipe executes the recorded
commands anyway, which is why 139 committed screenshots exist and why no gate
ever reddened: the screenshots are evidence about Mesa's leniency, not about
the submission. The reviewer's attribution is right and is repeated here: this
was pre-existing, not introduced by the range it was found in. It is reported
because batch 153's new B11 check had just certified the frame seam as sound.

THE FIX (`vk_context.cpp:1090`):

    const VkResult ended = vkEndCommandBuffer(frame.commandBuffer);
    if (ended != VK_SUCCESS) { drainPresentWait(ctx, frame); vkFailed(...); return false; }

Three things about that placement, each of which is a decision:

  * It sits AFTER `vkCmdEndRenderPass` — the render pass has to be closed before
    the stream is, and a stream ended with a render pass open is a different
    invalid use, not a smaller one.
  * It sits BEFORE `vkResetFences`. A refused frame has to leave its fence
    signalled (§5); the reset is the one call in `endFrame` that would take that
    away, so the refusal has to happen on the near side of it.
  * Its result is read and the frame is refused when it fails, for the reason the
    one-shot path already gives at `renderer_vk.cpp:342`: "a command buffer
    whose `vkEndCommandBuffer` failed is not finalised, and submitting an
    unfinalised command buffer is invalid use". The frame path simply never
    applied its own rule to itself.

What a FAILED end still costs, stated rather than hidden: the buffer is left
recording, and `vkResetCommandBuffer` on a recording buffer is invalid use
regardless of the pool's RESET_COMMAND_BUFFER_BIT, so the next frame is broken
too. Nothing un-records a buffer — there is no `vkUnbeginCommandBuffer` — and
the only recovery is a reset the spec forbids at that moment. It is printed
(`vkFailed("vkEndCommandBuffer(the frame's command buffer; nothing was
submitted)")`) rather than solved, because a driver that refuses an end on a
buffer it just let record has already told you the device is going.

2. F3 (High) — CONFIRMED, FIXED.
--------------------------------------------------------------------------------
Batch 152 stopped the CALLERS of `endOneShot` from releasing what an unfenced
submission names. It did not look at the callee. `endOneShot`'s tail ran, on
every outcome including `unfenced`:

    if (ended) vkFreeCommandBuffers(ctx->device, pool, 1, &cb);
    vkDestroyCommandPool(ctx->device, pool, nullptr);

`vkFreeCommandBuffers` requires that all submitted commands in the buffer have
completed (VUID-vkFreeCommandBuffers-pCommandBuffers-00047);
`vkDestroyCommandPool` requires the same of every command buffer made from the
pool (VUID-vkDestroyCommandPool-commandPool-00041). `unfenced` is precisely the
outcome that says that fact is unknown. So `createHostImage` correctly abandoned
the staging buffer and the image the copy may still be writing, and four lines
later the callee destroyed the command stream the copy is made of. The refusal
text at :384 even says "the memory it reads or writes is NOT safe to release"
— and the block comment below it reasoned about the RECORDING state (review-8
F6's subject), not about the in-flight one.

THE FIX (`renderer_vk.cpp:403`): the unfenced outcome returns before the
releases, and the pair is abandoned on the callers' terms for the callers'
reason — the handles stop being ours instead of being destroyed:

    if (result == OneShot::unfenced) {
        refused("one-shot command buffer and its pool are abandoned, not freed: "
                "the submission that may still be running is made of them");
        return result;
    }

The leak is two driver objects per failed wait, next to the image and the
staging memory the caller already abandons above, on a driver that fails a
wait; the pool is created TRANSIENT and is reclaimed with the device either
way. B10 now pins the callee as well as the callers, including that the guard
must sit BEFORE the releases and that `endOneShot` is still straight-line —
"before" only means "unreachable" in code with no loop, so the absence of a
loop is checked and not assumed.

3. F4 (Medium) — CONFIRMED, FIXED, RECORD CORRECTED.
--------------------------------------------------------------------------------
The comment batch 153 left at the two post-acquire exits in `beginFrame` said
the leftover acquire signal was "a stale +1 on a semaphore, not a leak and not
a hang". `presentWait` is created with a bare `VkSemaphoreCreateInfo` and no
type info, so it is a BINARY semaphore: it has two states and no count, and it
can never be +1. The reviewer is right that the sentence reasons about an
arithmetic the object cannot represent, and right that the consequence is not
benign: the next frame's `vkAcquireNextImageKHR` would pass an already-signalled
binary semaphore, which is invalid use (VUID-vkAcquireNextImageKHR-semaphore-
01779) with no specified driver answer.

The consequence was also under-recorded: the same posted semaphore is left by
`endFrame`'s submit-failure path, which batch 153 rewrote and did not mention.

THE FIX — the signal is consumed, not explained away. Vulkan cannot WITHDRAW a
signal from the CPU (`vkSignalSemaphore` can post one, nothing takes one back),
but it can CONSUME one: an empty submit — no command buffers, no signal, just
this wait, with a TOP_OF_PIPE stage mask because
VUID-VkSubmitInfo-pWaitDstStageMask-parameter requires one whenever there is a
wait — retires the signal as soon as the queue reaches it, and it reaches it at
once because the signal is already posted. `drainPresentWait` (`vk_context.cpp:70`)
is called from the five exits that hold a posted signal:

    beginFrame :1012  vkResetCommandBuffer failed
    beginFrame :1020  vkBeginCommandBuffer failed
    endFrame   :1092  vkEndCommandBuffer failed
    endFrame   :1114  vkResetFences failed
    endFrame   :1122  vkQueueSubmit failed

and deliberately NOT from the acquire-failure exits: on a failed acquire the
semaphore's state is not known, and waiting on a signal that may never arrive
would stall the queue instead of repairing anything. That indeterminate case
stays an open item, with the reason it stays.

4. F2 (High) — REBUTTED, with the premise pinned instead of argued.
--------------------------------------------------------------------------------
The finding: "`vkWaitForFences` at :929 succeeds and therefore RESETS the slot's
fence to unsignalled. Four subsequent exits return false without any submit, so
`frame.inFlight` stays unsignalled … The next `beginFrame` waits on that same
fence with `UINT64_MAX` and never returns."

The first clause is false, and the whole finding rests on it. Waiting on a
Vulkan fence does not reset it. `vkWaitForFences` reports whether the fence is
signalled and leaves it signalled; returning a fence to the unsignalled state is
`vkResetFences`, a separate call. The evidence in this file:

  * `createFrameResources` creates every `inFlight` with
    `VK_FENCE_CREATE_SIGNALED_BIT` (`vk_context.cpp:549`) — the initial state a
    free slot is supposed to have;
  * the ONLY `vkResetFences` in the file is at `:1112`, inside `endFrame`,
    immediately before the submit that will signal it again;
  * therefore every `return false` in `beginFrame` after the successful wait
    leaves the slot's fence SIGNALED, which is the invariant "this slot's fence
    is signalled when the slot is free", and the next `beginFrame` waits on a
    signalled fence and returns immediately. The slot is reused. Nothing hangs.

The reviewer's own comparison is what shows the distinction: the submit-failure
path in `endFrame` genuinely was a hang, and batch 153 fixed it, precisely
because THERE the fence had been reset for a submission that never happened.
The same recovery in `beginFrame` would be worse than unnecessary — it would
destroy a fence and allocate a replacement on a path that runs every frame on a
driver that has done nothing wrong.

No code changed for F2. What changed is that the premise is now pinned by C3
rather than argued in prose: C3 is red if `beginFrame` ever contains a
`vkResetFences`, and red if `endFrame`'s refused-submit path loses its
signalled replacement. Two arms, one per half, each naming C3. A comment at
`vk_context.cpp:963` states the invariant at the wait.
