THE CHANGE (one slice: the Linux render path's refusal reporting)
----------------------------------------------------------------
`mdk_linux/src/render/renderer_vk.cpp`
1. `refused()` now prints ONE LINE PER DISTINCT REQUEST. It formats the caller's
   varargs into a buffer, and keeps a bounded set (256 entries) of the requests
   each site has already named, keyed on the address of the site's own format
   literal — every call site passes a string literal, so the pointer is a free
   per-site id. A request already named returns before the printf; a new one
   prints and is remembered. Past the cap everything prints, because an
   unreported refusal is the bug and a repeated line is only noise.
   A SET is required, not a single "last message" latch: measured below.
2. `refused()` added at every remaining silent null-handle return: the one-shot
   command pool, the one-shot command buffer ALLOCATE (result now checked) and
   its BEGIN (result now checked), `vkAllocateDescriptorSets`, both
   `vkCreateGraphicsPipelines` sites (they printed, but without the `[vk]
   REFUSED` prefix and without the fflush B2 exists for), `createModule`
   (`vkCreateShaderModule`'s result was discarded, and its caller's guard is
   `if (!module)`, which an undefined out-parameter defeats), and both
   `vkCreateSampler` sites (a null sampler is every textured draw sampling
   nothing). The pipeline cache is deliberately left unchecked: it is an
   optimisation, and a run without one draws the same picture.
3. The three descriptor callers now SKIP the draw when there is no set, with a
   comment saying why: a missing picture is the failure this file reports, a
   wrong picture is not.
4. `createHostImage()` gained an `else` on `if (cb)`: it destroys the image and
   its memory, frees the staging pair, prints, and returns false. The caller's
   own refusal line then names the texture this one was meant to become.
5. The two frames-in-flight lines print the TOTAL and the per-slot figure
   ("(%llu bytes total, %llu per slot)"), so the number beside "x 2 frames in
   flight" is the number the driver was asked for (F3).

`mdk_core/src/game/object_draw.h` — comment only. The claim review-5 F1 proved
false is replaced by the claim that is now checked, and it says which gate checks
it and how (every `return VK_NULL_HANDLE` in the backend prints).

`tests/scripts/linux_refusal_report_test.sh` — 6 checks -> 10, 7 arms -> 13.
  B2 now accepts a helper that formats with `vsnprintf` (it must still take a
     va_list and flush).
  B3 reads the create call's size argument as an EXPRESSION and requires every
     size site to contribute; a printed figure may only be built from that
     expression and the frames-in-flight count (F4).
  B4 NEW, the discovery rule: every `return VK_NULL_HANDLE` in the file has a
     `refused(` before it in its own block. No list, whole file (F1).
  B5 NEW: every `vkAllocate*` call's VkResult is read (F1).
  B6 NEW: `createHostImage`'s null-command-buffer path refuses and returns
     false (F1).
  B7 NEW: the helper dedups, and dedups against a SET (F2).
  Two harness bugs fixed on the way: `call_args` counted brackets inside string
  literals, so a refusal message containing "(%llu bytes)" truncated its own call
  and the site silently dropped out of B3; and `blocks()` found a condition's end
  with `find(")")` instead of matching it. Both are why B3 could read "nothing".

STILL OPEN AFTER THIS BATCH
---------------------------
* Whether descriptor-pool exhaustion is REACHABLE in a real session is still
  unproven (review-5 open question 1). Nothing in this file frees a set:
  `vkFreeDescriptorSets`/`vkResetDescriptorPool` appear nowhere, and
  `forgetDescriptorSets()` drops only the CPU-side cache entry, so every
  released-and-re-made texture or palette consumes a set for the life of the
  process (`maxSets = 4096`). Proving reachability needs a counter or a free,
  which is a different slice from making the refusal audible when it happens.
* The dedup set is capped at 256 entries; past it every refusal prints again.
  A run with more than 256 distinct refusals is already a run whose device has
  nothing left, and a flood there beats silence.
* The `vkCreateImageView` failure path in `createHostImage` still leaks the image
  and its memory (it returns false without destroying them). That is a leak on a
  refusal path, not a silence, and it is not this batch's finding.
