1. F1 (Medium, CONFIRMED, REPRODUCED BEFORE CHANGING ANYTHING)
================================================================================
The positional verdict asserted only the NEAR corner: `inside` counted pixels with
cx <= CANARY_X1 and cy <= CANARY_Y1 and passed at >= CANARY_MIN (25). The far corner
bx1/by1 was computed, printed, and never compared. Reproduced against `git show HEAD`
of the harness, with the shipped panel_crop crop and the harness's own lifted block:

    block(0,0,27,11)  ->  HUD VISIBLE -- 297 canary pixels in the panel, 132 inside
                          the marker's rect 0,0-11,11 (bbox 0,0-26,10)        rc 0
    block(0,0,22,22)  ->  HUD VISIBLE -- 484 ... 144 inside (bbox 0,0-21,21)   rc 0
    block(0,0,11,11)  ->  HUD VISIBLE -- 121 ... 121 inside (bbox 0,0-10,10)   rc 0

The first two are a wrong-aspect HUD (what mdk_render_canvas_width returning 240
instead of 600 paints) and a marker twice too big. Both certified green while the
contradicting bbox was printed on the same success line.

THE FIX. The rect is now enforced from BOTH sides, so the printed bbox is part of the
verdict instead of commentary on it:

  CONTAINMENT  inside != total  ->  `HUD OVERSIZED`  (a pixel outside the rect)
  EXTENT       bx1 < REACH_X or by1 < REACH_Y  ->  `HUD UNDERSIZED`

CANARY_REACH_X / CANARY_REACH_Y = 10 = floor(10.667), the derived far corner without
the ceil slack CANARY_X1/Y1 = 11 already carry. Containment already implies
bx1 <= 11, so the pair pins the marker's bbox to [10,11] on each axis, which is the
extent the canvas's own width produces.

The UNDERSIZED arm is a hole the reviewer did NOT name and the same argument finds:
a canvasWidth too LARGE shrinks the marker so it sits wholly inside the rect and
still clears the floor (block(0,0,8,8) = 36 px, all inside, all counted). An
inside-count and a containment rule both pass it; only an extent test sees it.

After the fix, same three captures:

    block(0,0,27,11)  ->  HUD OVERSIZED ... bbox (0,0)-(26,10) reaching past it   rc 1
    block(0,0,22,22)  ->  HUD OVERSIZED ... bbox (0,0)-(21,21) reaching past it   rc 1
    block(0,0,11,11)  ->  HUD VISIBLE -- 121 ... (bbox 0,0-10,10,
                           reaching the derived (10,10))                          rc 0
    block(0,0,8,8)    ->  HUD UNDERSIZED ... must reach (10,10)                   rc 1

F1's SECOND HALF: the derivation was a second spelling, not an import. The test's
DERIVED block restated `far = size * sw / ch` by hand, so it could not notice the
renderer changing the thing it was written to pin. It now reads the return EXPRESSION
out of mdk_render_canvas_width's body, substitutes the constants it names, and refuses
(hard, not skipped) on an expression it cannot resolve. The two axes are derived
SEPARATELY — far_x = kSize*kScreenHeight/canvasWidth, far_y = kSize*kScreenWidth/
kCanvasHeight — because a canvasWidth error moves one and not the other, and a single
shared `far` hid that.

THE IMPORT IS PROVEN TO BE AN IMPORT, not asserted. The test mutates a COPY of
renderer_c3d.cpp, swapping the two screen axes in mdk_render_canvas_width (the exact
mistake that function's own comment warns turns 600 into 216), and requires the
derivation to MOVE and to move only the axis a canvasWidth error moves:

    real tree    ->  11 11 10 10
    mutant       ->  30 11 29 10        (far_x 10.667 -> 29.63, far_y untouched)
    check        ->  PASS (moved, and only on the axis that must move)

Had the test still been spelling the ratio by hand, the mutant would have derived the
same rect as the real tree and the row would have passed while certifying nothing.

2. F5 (Low, CONFIRMED) — malformed evidence certified green
================================================================================
`case "${total}${inside}" in ''|*[!0-9]*)` concatenated the two fields, so a stats line
whose FIRST field was blank and second numeric read as "all digits"; both comparisons
then died on "integer expression expected", no branch was taken, and the function FELL
THROUGH TO `HUD VISIBLE`. The replaced single-field guard failed closed. Reproduced:

    OLD: total="" inside="121"  ->  digits -> integer expression expected -> VISIBLE
    NEW: total="" inside="121"  ->  refused (fail-closed)

Each field is now validated on its own; a bad count resets to 0 (fails the floor) and a
bad bbox resets to -1 (fails the reach). A 5-field partial print, which the parent
certified as `HUD VISIBLE`, now reds. Four rows pin it by stubbing canary_stats,
because the point is the guard and not the Python that today always prints six fields.

3. F2 (Low, CONFIRMED) — the fixture was not the transform it named
================================================================================
Verified independently: the old `mirror` fixture built block(W-rx1, H-ry1, rx1, ry1)
= (389,229)-(399,239). A reflection about the panel's vertical axis maps (x,y) ->
(W-1-x, y) and would land at (389,0)-(399,10). The fixture's y is 229, so it is the
180-degree / opposite-sense disposition, determinant +1 — not the determinant -1
reflection the prose and the batch record both claimed.

The fixtures are now BUILT FROM THE SIGN PAIR. canvasMatrix's quarter turn is
`out col0 = a·m col1`, `out col1 = b·m col0` with the shipped (a,b) = (1,-1);
`disposition(a,b)` computes the corner from (a,b) through the mapping the harness
documents, and all four dispositions are rows:

    here    ( 1,-1)  shipped            det +1   ->  rc 0
    turn    ( 1,+1)  "drop the minus"   det -1   ->  rc 1
    flip    (-1,-1)  the other one      det -1   ->  rc 1
    rot180  (-1,+1)  opposite sense     det +1   ->  rc 1   (what `mirror` drew)

The marker's size also comes from the reach the harness DECLARES (REACH+1) instead of a
literal, so the fixtures move if the harness's derived rect ever does.
