THE FIX: a REACH arm, mirroring the one the marker's own verdict already had

origin). The ink is anchored at the FAR corner, so the arm is its mirror:

    if [ $(( bx1 + HUD_INK_REACH )) -lt "$HUD_INK_X1" ] \
       || [ $(( by1 + HUD_INK_REACH )) -lt "$HUD_INK_Y1" ]; then -> HUD NOT AT ITS ANCHOR

`HUD_INK_REACH=12`, and the budget is derived rather than picked:
  * the far corner is taken with ceil() (389.33 -> 390), which costs 1 px;
  * the ink is the farthest HUD-palette PIXEL and not the panel's bounding box, so
    whatever border texels of the sprite carry no (0,255,0) sit between the two;
  * on the shipped capture that shortfall measures **2 px on each axis** (bbox far
    corner 388,232 against the derived 390,234) — re-measured this batch, §4 below;
  * 12 is six times the measured shortfall and still only 18 canvas px, while the defect
    class this row chases displaces a HUD by hundreds. A budget at the measured 2 would
    red the moment the open texture-addressing fix changes which texels carry the colour,
    and a gate that cannot survive the fix it is waiting for gets deleted, not tuned.
The arm refuses on `<`, so the budget is INCLUSIVE, and there is a fixture on the
boundary (`inkreach`) pinning that.

F1's SECOND HALF, also fixed: the `outside` refusal blamed only the LEVEL for producing

3. F3 (Low) — CONFIRMED, FIXED. THE "ONE SPELLING, TWO BASES" RULE WAS APPLIED TO THE
   BBOX AND NOT TO THE COUNTS, AND BOTH OF ITS FAILURE MODES LANDED ON THE COUNTS.
--------------------------------------------------------------------------------
`decimal_measurement` tests digits, not bases, so a leading zero passes it; `[ 0133 -le N
]` is a DECIMAL comparison while `$(( inside + outside ))` is an ARITHMETIC one, which
reads the same field as OCTAL. Measured on the parent, same lifting method:

  count line `133 0388 0 333 206 388 232`
    PARENT: `0388: value too great for base (error token is "0388")`  rc=1  — the whole
            harness aborts with an UNNAMED failure, the exact hazard the block's own
            comment says `10#` prevents
    NEW:    `HUD MALFORMED: the ink count line is [...]: 388 inside a ...`  rc=1 — the
            designed refusal, by name (the line really is inconsistent: 388 != 133)
  count line `0133 0133 00 333 206 388 232`
    PARENT: `HUD MALFORMED ...` rc=1 — a legitimate measurement REFUSED, because
            `$(( 0133 ))` is 91 while `[ 0133 -le N ]` is 133
    NEW:    `HUD INK -- 133 of 133 ...` rc=0 — one spelling, two bases, one measurement

THE FIX normalises once, immediately after the fields are known to be digits:
`total=$(( 10#$total ))` and the same for inside/outside, and for the four bbox fields
where they are validated. Every comparison below and the line printed inside a green
verdict then read one number.

The row's real remaining defect is unchanged and is still item 1 of the NEXT list: the
panel sprite is sampled wrong by the GPU, by a factor of ~4 across its width. This batch
did not start it, on purpose. `C3D_Tex` carries no stride field, so the rule lives inside

upstream citro3d or disassembling `C3D_TexInitWithParams`/`C3D_TexBind`, and the row's own
open item says the rule must be pinned with a pattern fixture BEFORE any scale is touched.
Batch 173 already tried and rejected a /4 on measurement. Starting that investigation
inside a remediation batch would have been the batch-expansion the builder brief forbids,
