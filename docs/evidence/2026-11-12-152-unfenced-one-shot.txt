1. R8-F1 — the refusal said "not safe to release" and released on the next line
===========================================================================

THE FINDING, AS RUN. `endOneShot` returned `bool`. A bool has two values, so the
case "the queue accepted the work and the wait could not prove it finished" had to
share a value with "the queue refused the work". Both callers treated the shared
value as the second one and freed:

  parent (ec3b13b) renderer_vk.cpp:350  if (ok && vkQueueWaitIdle(...) != VK_SUCCESS) {
                       refused("... the staging memory it read is not yet safe to release");
                       ok = false; }
  parent :712-718  createHostImage:  vkDestroyBuffer(staging); vkFreeMemory(stagingMemory);
                                       vkDestroyImage(*outImage); vkFreeMemory(*outMemory);
  parent :925-931  captureSwapchain: vkUnmapMemory(memory); vkDestroyBuffer(buffer);
                                       vkFreeMemory(memory);

So the branch written to honour AGENTS.md P3 was the branch that violated it: "do
not overwrite, resize, or free an in-flight resource ... put the completion boundary
BEFORE CPU reuse". A failed wait is a completion boundary that was NOT established,
which is a different fact from a completion.

THE FIX. `endOneShot` returns `enum class OneShot { done, neverSubmitted, unfenced }`.

  done           the wait proved it — everything it named is safe to release
  neverSubmitted the queue refused it — safe to release, and the resource is refused
  unfenced       accepted, completion unknown — NOT this side of the boundary

`unfenced` releases nothing. `createHostImage` nulls its three out-handles and
returns false; `captureSwapchain` returns false without unmapping. The handles are
nulled because the function stopped owning them, NOT because they were destroyed, and
the comment says so in those words. The reviewer's own recommended remediation named
this option first ("leaking/retiring the pair otherwise").

Why abandon rather than retire: the file already has a retire list drained at the
frame boundary that proves the reading frame finished, and that is the right shape
for a mesh. It is the wrong shape here for two reasons that were checked rather than
assumed. (i) `createHostImage` takes a `mdk::vk::Context*` and has no renderer to
retire into — threading `RendererVk*` through it and its four call sites is a wider
diff than the finding. (ii) The readback buffer is persistently mapped and
`RetiredBuffer` carries no mapping, so retiring it would mean teaching the retire path
to unmap — and reading that path closely is what turned up a separate defect in it,
recorded at §10 rather than smuggled into this batch. Neither is a one-liner, and this
path cannot be executed to find out (see §8). The leak is bounded by the number of
failed waits, which is zero on every driver measured on this host.

One refinement: the wait is retried at device scope before declaring the outcome
unknown (`vkQueueWaitIdle(...) == VK_SUCCESS || vkDeviceWaitIdle(...) == VK_SUCCESS`).
A device-wide wait proves the same fact about this queue, so a queue-wait failure that
a device wait survives becomes a proven completion and the pair is freed normally. It
waits more than this queue — a stall — which is affordable on the one path where the
narrow wait has already failed.

WHAT THE CALLERS DO WITH IT (checked, not assumed):
  mdk_render_create_index_texture / _create_rgba_texture / _create_palette:
      the slot's handles are null, `used = false`, the id is refused. Nothing later
      destroys what was abandoned, because nothing holds it.
  mdk_render_update_texture: restores the OLD image/memory/view; the abandoned ones
      were nulled in the slot first, so they are not lost-and-tracked. The texture
      keeps its previous frame, which is what that refusal already promised.

===========================================================================

The reviewer could not produce the VUID and asked for a validation-layer run with a
forced end failure. Neither is available here: there is no spec copy on this host, no

experiment: the instrument is not on this machine.

What was done instead is the change that is safe under EITHER reading: the explicit
`vkFreeCommandBuffers` now runs only when the end succeeded. If the end failed, the
pool is destroyed and `vkDestroyCommandPool` reclaims every command buffer allocated
from it, recording or not — so nothing leaks under either reading, and the call the
finding questioned is simply gone. `vkResetCommandBuffer` was NOT added: the
documented reset of an individual command buffer needs
`VK_COMMAND_POOL_CREATE_RESET_COMMAND_BUFFER_BIT`, which this pool does not ask for, so
the reviewer's first suggestion would have introduced a different invalid use.

STILL OPEN: whether the removed call was in fact invalid. Recorded as unproven, not
as fixed.

10. A DEFECT FOUND WHILE JUSTIFYING THIS BATCH'S CHOICE — RECORDED, NOT FIXED
===========================================================================

To decide whether the unfenced pair could be handed to the existing retire list, the
retire path was read end to end. It cannot be the right home for a persistently mapped
buffer, and the reason it cannot is a defect of its own:

  renderer_vk.cpp:2158  mdk_render_release_mesh retires m.buffer[slot] / m.memory[slot]
                        for every frame in flight, and nulls m.mapped[slot]
  renderer_vk.cpp:2381  ensureCanvasBuffer retires the whole canvas ring the same way
  renderer_vk.cpp:282   settleRetired -> destroyBufferPair -> vkDestroyBuffer,
                        vkFreeMemory

Nothing on those paths ever calls `vkUnmapMemory`. Both buffers come from
`createHostBuffer`, which maps them for the whole lifetime (that is what `m.mapped[]`
and `r->canvasMapped[]` are), and nulling the CPU-side pointer is not an unmap. So the
frame boundary that is supposed to be the clean completion point frees memory that is
still mapped — the same shape as R8-F6, a lifetime rule asserted without the VU in
hand, and it runs on EVERY mesh release and every canvas resize rather than on a driver
failure.

Why it is not fixed in this batch: it is not one of the review's findings, it needs a
decision about the shape of `RetiredBuffer` (carry the mapping and unmap at settle
time, or unmap at retire time — and the two have different answers about whether the
CPU may still touch the pointer), and this batch already changes one lifetime rule.
It goes to CONTINUATION's next list with the three call sites and the two candidate
fixes, and it is the first thing to test if a validation layer ever gets installed on
this host.
