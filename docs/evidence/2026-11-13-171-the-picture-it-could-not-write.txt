== 1. THE DEFECT, MEASURED ON THE COMMITTED BINARY BEFORE ANYTHING WAS CHANGED ====

Review-2 F1 (Medium), reproduced on `94ce8d3`'s own build, `DISPLAY=:99`, level 3,

  --capture=$W/ok.bmp --capture-frame=1 --frames 2      (positive control)
      rc=0, [vk] screenshot: wrote … (320x240), 307254 bytes

CONFIRMED, not rebutted. The root cause is one discarded bool: `captureSwapchain()`
returns bool, `mdk_render_end_frame` called it as a statement
(mdk_linux/src/render/renderer_vk.cpp), and `main` returned 0 unconditionally. Batch
170 closed the reachability half (a capture frame the run could not reach); this is the
writability half, reached from a perfectly well-formed argument.

Why it matters more than a wrong exit code: the harness upstream checks that the file
it asked for exists, finds the BMP the PREVIOUS run left at that path, and commits it
as this build's frame. The sibling precedent the reviewer cited (tetrisphere-godot
`tools/pc/capture.sh`, "no root screenshot was written" → non-zero) treats exactly this
as a hard error.

== 2. THE FIX ================================================================

An accounting, not a printf.

* `RendererVk` gains `capturesRequested` / `capturesWritten`. The write counter rises
  ONLY in the branch where `captureSwapchain`'s own result decided it:
      } else if (captureSwapchain(r, path.c_str())) {
          r->capturesWritten++;
      }
  which covers a failed open, a short write, a failed readback, a mapping it could not
  make, and a frame that was never submitted (that path refuses and never counts).
* `mdk_render_capture_stats(MdkRenderer, int32_t* requested, int32_t* written)` is
  declared in `mdk_core/src/render/render.h` next to `mdk_render_stats` /
  `mdk_render_gpu_wait_ms`, and implemented in BOTH backends.
* `main` asks after the loop and fails the run when it asked for a picture and got
  none:
      if (captureFrame > 0 && captureWritten < 1) { … status = 1; }
  The rule is stated against what the RUN ASKED FOR and not against the backend's
  `requested`, because "the write failed" and "the frame was never reached" are the
  same failure from a harness's side. Teardown still runs before the return.

Why the query is in the shared seam and implemented twice: measured, every `mdk_render_*`
name in `render.h` is defined by BOTH `renderer_vk.cpp` and `renderer_c3d.cpp` (the
header's symbol set is a subset of each; only `mdk_render_present` is in neither list
because it is in both). A query declared in the shared header and defined in one backend
is a link error waiting for the next batch that calls it from shared code. The PICA
backend has no readback of a rendered target, so it counts a request in
`mdk_render_begin_frame` and can never report a write — the honest answer, following the
`mdk_render_gpu_wait_ms` "The 3DS backend reports 0" precedent already in the same
header, and not a stub returning success.

That is why `mdk_3ds/**` is in this diff, and why P8 emulator evidence is owed (§5).
