that mentioned LESS than the size. `kFramesInFlight`, `mdk` and `vk` are in

  review-6 F1(i), at the canvas site

The first is review-5 F3's defect exactly — a printed byte figure that disagrees

pins identifiers and the absence of a rescale, not arithmetic. `size + size`

2. F3 (Medium) — CONFIRMED, then fixed. B4 attributed per function, not per return.
===========================================================================
B4 asked whether `refused(` appeared anywhere between the innermost `{` and the
return. An unbraced `if (cond) return VK_NULL_HANDLE;` has no block of its own,
so its innermost `{` is the whole function body and any refusal the function had
already made vouched for it. Mutant, placed a few lines AFTER getDescriptorSet's
existing refusal:

    if (texture >= (int32_t)r->textures.size()) return VK_NULL_HANDLE;

against batch 149's gate:

    PASS LinuxRefusalReport (10 checks, 13 arms adjudicated red)

against the new gate:

    FAIL Linux backend: every null-handle return in the file is preceded by a refusal

The unbraced form is now handled on its own terms: only its condition can carry
the refusal, and a condition never does. A refusal followed by cleanup statements
before the return still counts, because that is how a refusal with something to
undo reads — `refused(...); vkDestroyCommandPool(...); return VK_NULL_HANDLE;`.
That was not free: the first version of the fix required the refusal to be the
statement immediately before the return and went red on all three of
`beginOneShotTracked`'s legitimate exits.

3. F2 (Medium) — CONFIRMED, then fixed. The pool was paired by position.
===========================================================================
`beginOneShotTracked` pushed the pool onto a file-scope `g_oneShotPools` and
`endOneShot` destroyed the front entry. Two exits returned VK_NULL_HANDLE after
the push without removing it, and `endOneShot`'s loop ended in an unconditional
`break`, so it always used index 0. One stranded entry and every later
`endOneShot` called `vkFreeCommandBuffers` with a pool the handle had not come
from — which Vulkan forbids — and destroyed that pool a step early.

Fixed by deleting the ledger rather than patching it: `beginOneShotTracked(ctx,
&pool)` hands the pool to the caller and `endOneShot(ctx, pool, cb)` takes it.
Both post-create exits now undo what they made (the begin exit frees the command
buffer too), and the vector is gone, which also removes the "never drained at
teardown" half of the finding. There is no pairing left to desynchronize.

New check B8 pins the shape: the pool is handed over, `endOneShot` frees and
destroys with the pool it was given and indexes nothing, and every null-handle
return after the pool exists has a `vkDestroyCommandPool` in its own block.
Three arms. Against batch 149's file it goes red on its own:

    FAIL Linux backend: the one-shot command buffer and its pool are handed over together

4. F6 (Low) — CONFIRMED, fixed, and the same shape was found in a second place.
===========================================================================
`createHostImage`'s staging-failure path freed `*outMemory` while it was still
bound to `*outImage`, then destroyed the image. The `else` branch batch 149
added did it in the correct order, so the function contained both orders. Fixed.
While fixing it, `createHostBuffer`'s map-failure path was found to have the same
inverted order; fixed too.

New check B9 pins the class coarsely and says so: in a block that both destroys a
buffer/image and frees memory, the last such call directly inside the block must
be the free. It does NOT prove the free releases that object's own memory, and
the comment states that instead of claiming more. Against batch 149's file:

    FAIL Linux backend: teardown frees the memory only after destroying what was bound to it

Run together against `git show HEAD:.../renderer_vk.cpp`, the two new checks red
exactly on the two defects and on nothing else.

5. F4 (Low) — CONFIRMED, fixed by removing the field rather than the claim.
===========================================================================
The comment asserted "the address of `fmt` IS the site: two sites cannot
collide". Identical literals are merged at -O1 and above, so that is false. The
`site` field could not do what the comment said, so it is gone and the key is the
rendered request alone. Two sites that render the same sentence now print one
line, which is the honest description of what the old key did in practice too.
Isolated harness of the helper, compiled -O2 -fmerge-constants:

    repeat of one request over 5 calls -> 1 line
    5 distinct requests                -> 5 lines
    two sites, identical words         -> 0 new lines (one fact, one line)
    two sites, different words         -> 2 lines
    400 distinct past the 256 cap      -> 400 lines, table stays 256

6. F5 (Low) — ACCEPTED as a documented asymmetry, not rebutted.
===========================================================================
The memory is for the life of the process, so a request that recovers and later
recurs byte-identically is silent. Re-arming needs a per-request success signal
this backend does not have, and clearing on a frame boundary restores the
22500-lines-in-one-run flood the set exists to prevent. The tradeoff is now
stated in the helper's comment and in `object_draw.h` rather than left implicit.
A refusal whose TEXT differs — a bigger canvas, a different texture — is a
different request and does print.

7. A harness bug the new check found by accident.
===========================================================================
`strip_comments` dropped any line whose first non-space character was `*`, on the
reasonable assumption that it was a block-comment continuation. It is also how
this file writes real statements: `*outImage = VK_NULL_HANDLE;` and the new
`*outPool = pool;`. The gate was reading a doctored file and reported that the
pool was never handed over when it was. `strip_comments` now tracks whether a
block comment is actually open. Every existing arm still reds on the corrected
text.
