BATCH 168 — ledger row `linux.render-frame`, acceptance `bash tools/check.sh`
THE 256-ENTRY REFUSAL MEMORY IS NOT REACHABLE HERE, AND NOT BECAUSE REFUSALS ARE
RARE: ON THIS HOST THE ALLOCATOR NEVER FAILS
=============================================================================

WHAT THIS IS
  Not a review remediation. CONTINUATION NEXT-list item 12, open since review-7 as
  "Is the 256-entry refusal memory reachable in one session?" — one line, deferred
  by every batch since because answering it needs a run, not an argument.
  Measurement batch: no file under `mdk_linux/**` or `mdk_3ds/**` changed, and no
  check changed. What changed is a question from open to answered, with numbers.

-----------------------------------------------------------------------------

-----------------------------------------------------------------------------

  So the answer to "is 256 reachable in one session" is: no, and the distance is
  not 256 vs 200, it is 256 vs ZERO. The dedup table never receives its first
  entry.

-----------------------------------------------------------------------------
2. WHY, AND WHY THAT IS THE INTERESTING PART
-----------------------------------------------------------------------------
  `refused(` has 38 call sites in `renderer_vk.cpp`, so the path is not dead code
  that nothing could ever reach. It never fires because **lavapipe does not refuse
  an allocation on this host** — not at 4096x3072, not at any level. The prior
  record already said this and this batch re-confirms it independently: the
  2026-11-12 evidence produced refusal lines only by FAULT INJECTION, "patching
  the allocator in a scratch build, running, and reverting", because "no executed
  arm can make lavapipe refuse".

  That reframes the item. The 256-entry memory exists to stop the flood review-5 F2
  measured at 22500 lines in one run. A flood requires refusals to recur, recurring
  refusals require an allocator that fails, and this allocator never fails. So the
  property the cap protects is not exercised by any unpatched run on this host, and
  the cap's own bound is unreachable by the same fact. Both halves of that are
  measured now: the count is 0, and the reason it is 0 is known rather than assumed.

-----------------------------------------------------------------------------
3. WHY NO GATE WAS ADDED, WHICH IS THE DECISION IN THIS BATCH
-----------------------------------------------------------------------------
  The tempting move is to pin "a session emits zero `[vk] REFUSED` lines". **This
  batch deliberately does not**, and the reason is AGENTS §2's argument about the
  staleness clocks, applied here: a gate that is green only while the frontend keeps
  never refusing is a gate that goes permanently red the first time a real ICD, a
  validation layer (NEXT item 7), or wired sprite churn makes the path fire — and a
  permanently red gate is worse than no gate, because it trains the reader to skip
  it. The measurement is a fact about this host's ICD, not an invariant of the code.
  The existing shape check already pins the properties that ARE invariants: that the
  set is consulted before printing, that the cap bounds the table, and that the
  print is followed by a flush.

-----------------------------------------------------------------------------
4. WHAT THIS DOES NOT PROVE
-----------------------------------------------------------------------------
  * It does not prove the refusal pipe works end to end on an unpatched build,
    because nothing on an unpatched build can make it fire. The only end-to-end
    demonstration on record is the 2026-11-12 fault injection. This batch adds a
    second independent confirmation of the NEGATIVE (zero refusals) and does not
    claim the positive.
  * It does not make the descriptor-pool exhaustion (item 11) reachable; that needs
    `sprite_residency_bytes` or the scope API wired on Linux, which is a different
    gap.
  * `--level 99` running at all, with the same startup draw count as level 3, is a
    separate oddity noticed during this measurement and NOT chased: it suggests an
    unknown level falls back rather than erroring. Logged as an open item rather
    than quietly filed under "works".

CORRECTION BLOCK — appended by batch 169, not a silent rewrite
=============================================================================
  TWO OF THIS FILE'S CLAIMS ARE ARTIFACTS OF AN ARGUMENT BUG, NOT MEASUREMENTS.

  `optionValue()` in mdk_linux/src/main.cpp matches `--name=value`. `--level` is
  not `--level=`. An unrecognized argument fell through the parse chain silently
  and the run continued on its default, level 3. So:

  1. Section 1's "levels 1..7, 300 frames each" was never a sweep. All seven runs
     received no level and ran level 3. The file records each of them ending
     "exiting after 300 frames (last frame: 190 draws, 1469 triangles)" — the
     identical draw and triangle count seven times, which is the tell, present in
     the table and unread. The CONCLUSION survives: batch 169 re-ran the sweep
     with the spelling the frontend accepts and every shipped level 3-8 still
     emits zero refusals (draw counts 190 / 28 / 107 / 87 / 153 / 243, i.e. six
     different scenes this time). See docs/evidence/
     2026-11-13-169-name-it-or-dont-run-it.txt section 1.

  2. Section 4's "NEW, not chased" and section 7's open item — that `--level 99`
     runs with the same startup draw count as level 3 and so "an unknown level
     falls back rather than erroring" — describe no behaviour of the frontend.
     `--level=99` refuses with "[main] --level must be 3-8" and rc 1. There is no
     silent fallback. The open item is closed as one that never existed.

  What this file measured correctly stands: on this host lavapipe never refuses an
  allocation, so the 256-entry refusal memory receives no entry and the whole-log
  census of a 600-frame level-3 run is [main] x10, [audio] x1, [vk] x0. That
  measurement used `--level 3` only, where the default happened to agree with the
  intent, which is exactly why it looked fine.
