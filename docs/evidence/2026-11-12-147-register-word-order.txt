them as (x, y, z, w). That is the canvas bug, the identity-matrix bug, and the

1. THE LIBRARY FACT, FROM THE SHIPPED BINARY, NOT FROM MEMORY
--------------------------------------------------------------------------------
(a) `/opt/devkitpro/libctru/include/c3d/types.h:37-64` — `C3D_FVec` is
    `struct { float w; float z; float y; float x; }` with the header's own note
    "Matches PICA layout". So offset 0 = w, 4 = z, 8 = y, 12 = x.

(b) `Mtx_Scale` (libcitro3d.a, mtx_scale.o), disassembled:

      4: vldr s13, [r0, #12]      ; the four loads of row i
      8: vldr s14, [r0, #8]
      c: vldr s15, [r0, #4]
     10: vmul.f32 s13, s13, s0    ; s0 = the x argument
     14: vmul.f32 s14, s14, s1    ; s1 = y
     18: vmul.f32 s15, s15, s2    ; s2 = z

    The x scale multiplies offset 12 of every row. `.x` is the LAST word.

(c) `Mtx_Translate` (mtx_translate.o), the `multiply == false` fast path, is
    `row_i[k] += row3[k] * t_i` for i = 0..2 (outer loop r1 = mtx+0..+48 step 16,
    inner loop r2 = mtx+48..+64 step 4, s13 = sx, sy, sz). Applied to the identity
    that yields row0 = (x=1,y=0,z=0,w=sx), row1 = (x=0,y=1,z=0,w=sy),
    row2 = (x=0,y=0,z=1,w=sz) — the translation matrix in the column-vector
    convention, i.e. the translation lives in each row's `.w`, which is offset 0.

(d) `Mtx_OrthoTilt` (mtx_orthotilt.o) writes, for `tilt != 0`:
      offset 0  = (top+bottom)/(bottom-top)      ; row0.w
      offset 8  = 2/(top-bottom)                ; row0.y
      offset 16 = (left+right)/(right-left)     ; row1.w
      offset 28 = 2/(left-right)                ; row1.x
      offset 36 = 1/(far-near), offset 32 = ((near+far)/2/(near-far)) - 0.5
      offset 48 = 1.0                           ; row3.w
    Read as (x,y,z,w) that projects the scene with x and z swapped and no y term
    at all. Read as (w,z,y,x) it maps y in [bottom,top] onto clip [-1,+1] and x
    onto -y, determinant +1 — which is what a Tilt matrix is documented to do.

(e) NOTHING REORDERS ON THE WAY OUT.
    `C3D_FVUnifMtxNx4` (c3d/uniforms.h:30-36) is `ptr[i] = mtx->r[i]`, a struct
    copy, and `C3D_UpdateUniforms` (uniforms.o) issues, for each maximal dirty
    run,

      d0: ldr  r3, =C3D_FVUnif
      e0: lsl  r2, r7, #2          ; total_words = count * 4
      e4: add  r1, r3, fp, lsl #4  ; param = C3D_FVUnif[stage] + start*16
      e8: bl   GPUCMD_Add

    The staging buffer is handed to the GPU verbatim. Therefore the word citro3d
    calls `.x` — offset 12, the LAST of the four — is the word the shader dots
    with `px`, and the word at offset 0 is the one multiplied by 1.

(f) THE HARDWARE-VALIDATED SIBLING AGREES AND SHOWS WHY IT NEVER BIT IT.
    `../forsaken/render_c3d.c:1121` `matrix_to_c3d` writes the NAMED fields:

        dst->r[i].x = m[0 + i];   dst->r[i].y = m[4 + i];
        dst->r[i].z = m[8 + i];   dst->r[i].w = m[12 + i];

    i.e. register i's (x,y,z,w) = column i of the engine matrix, top-down — the
    same intent MDK's comment states. Forsaken could not hit the bug because it
    goes through the names, and the names are already reversed in memory. MDK
    wrote the same sequence into `C3D_Mtx::m[]`, the raw view, where the same
    order is the reverse order.

CONSEQUENCE. For the engine's row-major row-vector matrix M, register i must hold
column i, so the words must be written [M[3][i], M[2][i], M[1][i], M[0][i]].
The shipped code wrote [M[0][i], M[1][i], M[2][i], M[3][i]]: every register
reached the shader component-reversed, with the engine's TRANSLATION row in the
slot the shader dots with x and row 0 in the slot it multiplies by 1.

2. THE THREE MEASURED SYMPTOMS IT EXPLAINS, EACH ALREADY IN THE RECORD
--------------------------------------------------------------------------------
(i) IDENTITY PAINTS NOTHING. registers(I) under the old order gives every
    register (x,y,z,w) = (0,0,0,1), so every vertex maps to the single clip point
    (1,1,1,1). `mdk_3ds/shaders/mdk_c3d.v.pica` records exactly this and calls it
    unexplained: "why the diagnostic triangle drawn through an IDENTITY matrix
    paints nothing at all".

(ii) THE CANVAS PAINTS NOTHING. `pica::canvasMatrix(600)` is
        row0 = [0, -0.003333, 0, 0]   row1 = [-0.005556, 0, 0, 0]
        row2 = [0, 0, 0, 0]           row3 = [1, 1, -0.5, 1]
    so the intended registers are (0,-0.005556,0,1) (-0.003333,0,0,1)
    (0,0,0,-0.5) (0,0,0,1) and clip = (1 - 2py/360, 1 - 2px/600, -0.5, 1).
    Reversed, the shader gets (1,0,-0.005556,0) (1,0,0,-0.003333) (-0.5,0,0,0)
    (1,0,0,0), i.e. clip = (px, px, -0.5px, px): clip x = clip w, so NDC x = 1
    and NDC y = 1 for every vertex, and the whole HUD collapses onto one panel
    corner. Batch 145 measured the buffer holding exactly the intended rows and
    concluded "the CPU side is correct at the instant before the draw" — it was,
    and the shader still read them backwards, because the buffer's word order was
    the bug. That is why every probe that read the buffer could not see it.

(iii) THE SUNBURST. `docs/evidence/2026-11-12-145-shipped.png` is 96000 px of
    painted panel and no readable view. That is what a level looks like with its
    MVP's components permuted. The open item that called itself "the one-sided
    view" is the same defect, not a separate one.

3. THE FIX AND ITS PIN
--------------------------------------------------------------------------------
`registers()` now writes

        out[i*4+0] = m[3*4+i];   // register w
        out[i*4+1] = m[2*4+i];   // register z
        out[i*4+2] = m[1*4+i];   // register y
        out[i*4+3] = m[0*4+i];   // register x

`shaderRow` in the host suite is the model of the hardware, and it said the
opposite, which is the only reason the suite was green: the layout row and the
shader row were two wrongs that cancelled. `testTheShaderReadsTheRegistersTheWay
TheMatrixMeansThem` keeps its assertion (`shaderRow(reg, i, p) == want[i]`)
unchanged; only the model changed. THE SUITE IS NOT WEAKER AFTER THIS CHANGE —
with the old `registers()` and the corrected model it goes red:

    FAIL pica_matrix:311: allEqual(reg, want, 16)
    FAIL pica_matrix:327: shaderRow(reg, i, p) == want[i]     (x3)
    3 check(s) FAILED

and with the fix, `PASS PicaMatrix`, 95 PASS / 0 FAIL for `build/vm_tests`.
No golden changed. The end-to-end pin is the console run below, which no host
test can substitute.
