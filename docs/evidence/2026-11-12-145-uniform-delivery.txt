================================================================================
WHAT IS NOW MEASURED, IN ONE SENTENCE
================================================================================
A vertex-shader uniform written by `installEye` reaches the shader — the level
renders, and it renders through the identical `registers()` +
`C3D_FVUnifMtx4x4` path. A vertex-shader uniform written later in the same
frame, after `installEye`'s `C3D_BindProgram`, does not: every canvas-space
vertex is therefore projected by the level's camera and lands off-panel. One
program, one uniform, one ordering difference, and the level is fine while the
HUD is empty.

**AND IT IS BIGGER THAN THE HUD.** `drawRecorded` composes and writes
`MeshDraw::world` per draw for exactly the same reason (batch 142's
object-placement fix). If post-`installEye` uniform writes do not land, no
object is placed by its world matrix either. The arena batch and Kurt carry
identity worlds, which is why the level looks right and nothing else noticed.
Any fix must be checked against object placement, not only against the HUD.

**WHY citro3d's OWN BOOKKEEPING DOES NOT EXPLAIN IT, RECORDED SO IT IS NOT
RE-DERIVED.** `C3D_UpdateUniforms` is called only from `C3Di_UpdateContext`
(`arm-none-eabi-objdump -dr drawArrays.o base.o`), and `C3Di_UpdateContext` is
the first call inside `C3D_DrawArrays` (also `C3D_DrawElements` and
`C3D_ImmDrawBegin`), and the `u16` gate at `__C3D_Context+0x208` falls through
to the uniform update on every path. So citro3d says a per-draw flush happens.
The measurement says the value does not arrive. The measurement wins.

**AND THE VAULT SHOWS THE PATTERN IS SUPPOSED TO WORK, WHICH IS THE MOST USEFUL
THING IN THIS FILE.** The devkitPro example recorded at
`/mnt/nas/Vaults/port-docs/60-references/3ds-platform/citro3d/01-overview-and-init.md:179-186`
is

    C3D_FVUnifMtx4x4(GPU_VERTEX_SHADER, uLoc_projection, &projection);
    C3D_DrawArrays(GPU_TRIANGLES, vertex_list_count);

with the program bound once in `sceneInit` and never re-bound. **Write-then-draw
with no re-bind is the library's own shipped usage, and it works there.** So the
sentence above is a measured SYMPTOM INSIDE MDK'S FRAME, not a citro3d rule, and
the next iteration should hunt for what in MDK's frame breaks the example's
pattern. The candidate that the archives hand over for free: MDK calls
`C3D_BindProgram` once per eye per frame, and `C3D_BindProgram` calls
`C3Di_LoadShaderUniforms` on EVERY call including the `beq` path taken when the
program is already current (`arm-none-eabi-objdump -dr base.o`, `C3D_BindProgram`
+0x24 `beq ac` → `ac: bl C3Di_LoadShaderUniforms`), which re-arms the shader's
own param-data upload every frame. The example binds once; MDK binds every
frame.

judge on is the level-sized signal, not the canary.

Run 7 named "give the canary the same 5-float layout a `drawRecorded` mesh uses"

Identical stride, identical attribute count, identical `0x10` format, and both
share the one `AttrInfo_AddLoader` pair installed by `installEye` (position =

it is `GSPGPU_FlushDataCache`'d before the draw, so the GPU can read it and the
P3 cache obligation is met.

**So the vertex-layout suspect is closed without a run.** What is left standing
between the one green run and the red ones is narrower than "geometry" and
narrower than "uniform": run 2 (matrix as `.constf` literal, canary at centre)
painted 100 px, and run 3 (same values, same geometry, matrix through

therefore **which function issues the write and when in the frame**, not the

statement — they are not the same sequence — rather than rebuild the canary's
