WHAT THAT MEANS, and it is not a small thing for this project's evidence.

1. **A full-RGB panel diff is not reproducible across runs of the same build — on
   THIS scene.**
   The capture is not frame-locked: `emurun.sh --shot` grabs the X window at a
   wall-clock deadline, and the guest prints a frame line only every 60th frame,
   so the frame actually on screen at the deadline sits anywhere in a ~60-frame
   window. The level-7 camera and object list are static but the textures animate,
   so that window repaints most of the panel's colour.

   **[ANNOTATED BY BATCH 105, review-11 F2.]** The last sentence states a
   mechanism the same batch declared unestablished, and it sits immediately above
   the retraction below so a reader meets it as fact first. What is measured here
   is the WINDOW (the capture is not frame-locked) and the SIZE (53515 px). That
   the window repaints "most of the panel's colour" because "the textures
   animate" is a hypothesis: batch 104 localised the movement to the object pass,
   and the differing pixels are 423-438 distinct colour pairs one step apart with
   R identical at 255, which is not what an animation phase predicts. The
   mechanism is an open item in `docs/CONTINUATION.md`, not a fact of this file.

   **[RETRACTED BY BATCH 104, review-10 F2.]** This paragraph went on to say that
   batch 102's "the noise floor is EXACTLY zero" **does not reproduce** and that
   "a control that prints 0 px was comparing a capture with itself". The second
   half is false. Batch 102's control was two genuinely independent runs — two
   lanes, two window grabs, and
   `docs/evidence/2026-11-09-L7-object-pass-parent.txt:29` names the second
   capture (`/tmp/kilo-b102/parent2.png`) — and its panel crops really were
   byte-identical. What the two numbers actually say is narrower and it is the
   lesson: **a noise floor is only valid for the scene it was measured on.**
   Batch 102's 0 px floor is the arena-only panel; this pair's 53515 px floor is
   the arena+objects panel. Batch 103 quoted a floor from a static scene at an
   animated A/B, and that is the mistake, not a self-comparison.
   The consequence for prior sidecars stands: every one that quoted a full-RGB diff
   as its picture claim, batch 102's 58520 px included, is quoting a quantity that
   is not a control on an animated scene.
2. **The painted-versus-clear map IS reproducible here** (0 px), and the census's
   exact clear-colour count has reproduced across batches. **[Amended by batch 104,
   review-10 F1: on THIS build the map is a constant — both runs are 96000/96000
   painted — so 0 px here is arithmetic and not a reproduction. The map is a
   control only where the panel has both painted and clear pixels, which is why
   `panel_geom.py geom` now refuses a degenerate side with exit 3.]** Where it is
   not constant it is the quantity a console A/B can claim, and
   `tools/panel_geom.py` is the one place that prints it, with the full-RGB number
   printed next to it and labelled.
3. A real console A/B therefore needs TWO runs per side, and the parent-vs-parent
   number is the floor the child-vs-parent number has to clear. One run per side
   supports a geom claim and nothing else.

what this pair CANNOT say: it does not say the panel instrument is useless, and it
does not retroactively invalidate the census numbers (58464 clear in both builds,
painted-left 0 in the arena-only build) — those are painted/clear numbers, the
half that reproduces. It says the colour half was never a control. The fix that
would make the colour half usable is a frame-locked capture, and the named blocker
is that the 3DS backend has no screenshot path at all (`render.h`: `screenshot_path`
is "Linux only"), so nothing in the guest can pin the frame.
