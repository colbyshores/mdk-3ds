1. WHAT WAS MEASURED, AND WHAT WAS DELIBERATELY NOT CLAIMED
-----------------------------------------------------------------------------
The item's premise is true. `destroyBufferPair` is `vkDestroyBuffer` +
`vkFreeMemory`, and `vkUnmapMemory` appears in this file only on the staging
paths (`createHostImage`'s staging copy, the readback), never on the retire path.
Both persistent-mapping owners — `MeshVk::mapped[kFramesInFlight]` and
`RendererVk::canvasMapped[]` — hand their mapping to a retire and never unmap it.

Whether an explicit `vkUnmapMemory` is REQUIRED before `vkFreeMemory` is a
question about the Vulkan specification's valid-usage text. This host has no
spec, and the vendored `vulkan_core.h` carries no prose (measured in batch 165:
`grep -c "Valid Usage"` is 0). Review-10 F3's entire lesson was that a quoted or
implied spec sentence nobody here can look up is a claim wearing a citation's
clothes. So **this batch does not settle that question and does not pretend to.**
The check's own message says so out loud, so a future reader cannot mistake the
silence for a verdict.

What IS decidable in the tree, and what the hazard actually turns on, is narrower
and is now pinned: a mapping pointer must not outlive the retire that took its
buffer, because nothing downstream can tell a live mapping from a released one.

Measured on the parent, before writing anything:
  - `retireBuffer` is called from exactly two places, `mdk_render_release_mesh`
    and `ensureCanvasBuffer`, and BOTH already null the slot's mapping field
    (`m.mapped[slot] = nullptr`, `r->canvasMapped[i] = nullptr`).
  - The only reader of a mapping local, `mdk_render_update_mesh`, already takes
    `void* mapped = m.mapped[slot]`, tests it for null, REFUSES by name, and
    returns before the `memcpy`.
So the implied hazard — a stale mapping dereferenced after the free — does not
exist on the parent either. Item 10 was a shape observation wearing a defect's
clothes, and the honest closure is to pin the property that keeps it a shape
observation, not to invent a fix for a bug that is not there.

2. CHECK B14, AND WHY IT IS SHAPED LIKE THAT
-----------------------------------------------------------------------------
  (a) DISCOVERED, not listed, exactly as in B13(c): every `retireBuffer` call in
      the file that names a slot must null that slot's mapping field later in the
      same function. The rule reads the slot out of the call's own argument and
      looks for the nulling of the matching `...[Mm]apped[...]` field, so it
      covers `m.mapped[slot]` and `r->canvasMapped[i]` with one pattern and will
      cover the third drop site nobody has written yet. A named list of the two
      current sites is the mistake B4 made in review-5.
  (b) every local taken from a mapping must be tested for null, behind a
      `refused(`, before anything `memcpy`'s through it. A null mapping copied
      through is a segfault in a release build; the refusal is what turns it into
      a mesh that keeps its previous contents and a line saying so, which is the
      difference B1 exists to make.

Four arms, each isolating B14:
  `retire-buffer-leaves-the-mapping-set`      the mesh slot's mapping left set
  `canvas-retire-leaves-the-mapping-set`      the canvas ring's, which is the site
                                              a future drop site gets copied from
  `mapping-copied-without-a-null-test`        the guard deleted: memcpy into null
  `mapping-guard-refuses-silently`            the guard kept and the sentence
                                              deleted: the silent-empty-mesh
                                              failure B1 was written for

`LinuxRefusalReport` is 20 checks / 67 arms / 5 probes -> **21 checks / 71 arms /
5 probes**.
