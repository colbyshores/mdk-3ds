1. F1 (Low, CONFIRMED, FIXED) — THE COUNTS AND THE BBOX WERE NEVER COMPARED
--------------------------------------------------------------------------------
Quote (review-4 F1): "The new relations arm closes `inside <= total` and
`inside <= 144`, but not the relation between the counts and the **bbox**.
`canary_stats` derives the bbox from the same pixel set whose size is `total`,
so `total` can never exceed the bbox area."

Reproduced against `git show HEAD` of the harness, with `canary_stats` stubbed
and the real lifted `canary_verdict`:

    121 121 10 10 10 10  ->  rc 0  HUD VISIBLE -- 121 canary pixels in the
                                  panel, 121 inside ... (bbox 10,10-10,10)
    121 121 11 11 11 11  ->  rc 0  (same)

A ONE-pixel box holding 121 pixels, printed inside the acceptance evidence.

1b. THE MIRROR, WHICH THE REVIEWER DID NOT NAME
--------------------------------------------------------------------------------
The same contradiction with the other sign was green too, and it is a larger
hole than the one reported: the containment arm returns unless inside == total,
and `inside` counts a pixel only when cx <= CANARY_X1 and cy <= CANARY_Y1, so
by the time the bbox is read EVERY counted pixel is inside 0,0-11,11 — yet the
bbox was free to say otherwise.

    121 121 0 0 12 12  ->  rc 0  HUD VISIBLE ... (bbox 0,0-12,12)
    121 121 0 0 11 12  ->  rc 0
    121 121 12 0 12 10 ->  rc 0

1c. THE FIX — TWO RELATIONS, BOTH GUARANTEED BY CONSTRUCTION
--------------------------------------------------------------------------------
One arm, placed after the bbox's own validation (so bx0<=bx1 / by0<=by1 are
already proven and neither difference can be negative) and after containment:

    [ $(( (bx1 - bx0 + 1) * (by1 - by0 + 1) )) -lt "$total" ]  ->  MALFORMED
    [ "$bx1" -gt "$CANARY_X1" ] || [ "$by1" -gt "$CANARY_Y1" ] ->  MALFORMED

Neither can false-red, and that is the property that matters in an acceptance
command:
  * area >= total — the bbox is the min and max over EXACTLY the counted
    pixels, so every counted pixel lies in the box; distinct pixels are distinct
    (cx,cy) pairs, so total <= area. Not a threshold: an identity.
  * bbox <= rect — containment already returned for any pixel outside the rect.

The area is at most the panel's own 400 x 240 = 96000, so the arithmetic cannot
overflow, and both bounds are the harness's OWN rect constants, which the host
test re-derives from the shipped renderer.

After: all five impossible lines above are `HUD MALFORMED` at rc 1, and the
honest ones are untouched — `121 121 0 0 10 10` (the real measurement),
`121 121 0 0 11 11`, `26 26 0 0 10 10` and `25 25 0 0 10 10` (sparse but
possible: 26 pixels with a bbox of 121 cells is a hole-y set, not a
contradiction) all still pass. The ordering pin holds: `0 0 - - - -` is still
`HUD NOT VISIBLE`, because the count arms run before the bbox arms.


2. F2 (Low, CONFIRMED, FIXED) — THE LENGTH ARM MEASURED THE STRING, NOT THE NUMBER
--------------------------------------------------------------------------------
Quote (review-4 F2): "The length arm `[ \"${#1}\" -le \"${#2}\" ]` is justified
as 'a field with more digits than its bound cannot be <= it'. That is false for
zero-padded input, and unlike the measurements it guards, `--min-frames` is
*caller-supplied*."

Reproduced against the shipped script:

    emurun: --min-frames requires a decimal 0..999999, got [0000060]   rc 2
    mdk_3ds/tools/emurun.sh: line 182: $2: unbound variable           rc 1

Two separate defects, one rule behind each.

2a. PADDING. The length arm exists so the `[ -le ]` under it can always be
EVALUATED — it is a REPRESENTABILITY test, not a size test. Padding adds
characters and no magnitude, so `0000060` (the exact shape a wrapper gets from
`printf '%06d'`) was refused as a usage error over a number that compares
perfectly well. Verified: bash's `[ ]` parses leading-zero operands as DECIMAL
(`[ 0000060 -eq 48 ]` is false, `[ 099 -le 999999 ]` is true), so the value was
never the problem; the character count was. The zeros are now stripped before
the length arm, and the comparison is made on the stripped value so the two arms
agree. No refusal is lost: a sign, a space or a letter is not a leading zero, so
`+121`, `-0`, ` 121`, `60x` and `1000000` are all still exit 2 (re-checked).
Padding smuggles nothing past a bound either: `0000096001` in a 96000-pixel
panel is still a refusal, because the bound is applied to the VALUE.

2b. A MISSING VALUE. Every option arm read "$2" under `set -u`, so a flag that
lost its argument aborted with `$2: unbound variable` and exit **1** — a code
this file does not document, from a shell internal, on the one path the caller
was promised 2. `need_value <flag> <argc>` now guards every value-taking flag
(`--secs`, `--grep`, `--shot`, `--min-frames`, `--expect`, `--display`), because
the bug was the shape of the arms and not any one of them. All six now exit 2
with a message naming the flag, and the shell's own fault string is gone.

4. OPEN QUESTION 2 CLOSED (review-4's own, not a finding) — ONE SPELLING, TWO BASES
--------------------------------------------------------------------------------
`CANARY_MAX_INSIDE=$(( (CANARY_X1 + 1) * (CANARY_Y1 + 1) ))` is bash ARITHMETIC,
which reads `011` as OCTAL, while every other reader of those constants is a
`[ -le ]`, which reads `011` as DECIMAL eleven. Measured: with a padded rect the
old expression gives 100 and the new one gives 144. A `CANARY_X1=011` edit would
therefore have derived 100 and refused the honest 121-pixel marker as
`inside > CANARY_MAX_INSIDE` — a false-red on the ledger row, caused by a
leading zero nobody meant. Now `10#`-qualified.

What it costs, stated rather than hidden: `10#` makes a NON-numeric rect constant
a load-time bash arithmetic abort (rc 1) where it used to evaluate as a variable
name and reach the named `HUD MALFORMED` constant check. Both are refusals and
neither is a silent pass, and the host test reddens a bad constant before it
ships (its derivation row re-reads the rect from the shipped renderer, and its
mutation row would not land).

The pin MUTATES A COPY of the harness with a padded rect and requires the derived
value to stay 144, with a non-vacuity row proving the mutation landed — because
restating the formula in the test would be the second spelling this file exists
to prevent (batch 156's lesson, learned once already).
