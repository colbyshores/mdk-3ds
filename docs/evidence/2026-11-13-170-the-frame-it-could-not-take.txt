§2. THE FIX
--------------------------------------------------------------------------------
`mdk_linux/src/main.cpp`, two refusals placed AFTER the whole option loop:

  if (captureFrame > 0 && capturePath.empty())
      → "[main] --capture-frame must be used with --capture: no file was named"
  if (captureFrame > 0 && maxFrames > 0 && captureFrame > maxFrames)
      → "[main] --capture-frame must be within --frames: frame %d is past the
         %d-frame bound and would write no picture"

AFTER the loop, not inside the branches, because the two options may arrive in
either order and a branch-local check catches only one of them. The reversed
order is a test row (§4, arm 16) precisely so that placement is pinned and not
merely asserted.

The bound is `>`, not `>=`: the loop increments `frame` and THEN tests the bound,
so frames 1..maxFrames all run and a capture frame equal to the bound is the
last reachable frame. Arm 23 pins that boundary from the accept side.

Side effect worth naming: a non-zero capture frame now always has a path behind
it, so the loop's own `captureThisFrame` break can no longer truncate a run for
nothing. The loop was not edited — the parser made the shape unreachable.

§3. F7 — ERANGE, FIXED, AND ITS LIMIT STATED RATHER THAN HIDDEN
--------------------------------------------------------------------------------
`positiveCount` proved `[1, INT_MAX]` with a `long`. Where `long` is 32 bits
(any -m32 / ILP32 build) `LONG_MAX == INT_MAX`, so `strtol` clamps, sets ERANGE,
and `value > INT_MAX` cannot fire: an out-of-range count is silently accepted as
the largest legal one — the fail-open the predicate exists to remove, arriving
through the type instead of the parse. `errno = 0` + `errno == ERANGE` now
refuses it, in `positiveCount` and in the sibling `--seed` path the reviewer
named as the same shape.

HONEST LIMIT, measured: on this x86-64 host `long` is 64 bits, so the old bound
test already refused `--frames 99999999999999999999` and
`--seed 99999999999999999999`. The two new arms therefore PASS ON THE PARENT TOO
(see §5, row 2: only 3 of the 6 new arms red). They pin the refusal; they do NOT
prove the ERANGE branch, which is not observable on this target and is not
claimed to be. The fix is a portability guard for a build this loop does not make.

§8. F4 (Medium) — HALF REBUTTED WITH EVIDENCE, HALF CONFIRMED AND OWNER-PROTECTED
--------------------------------------------------------------------------------
CONFIRMED: CPython's `subprocess.run` on timeout calls `process.kill()` and then
`process.wait()` with no timeout on the POSIX path, so a child in a genuinely
unkillable wait still blocks, and the 120 s is advisory rather than a hard bound.

REBUTTED: "TimeoutExpired is uncaught, so a stall that IS bounded surfaces as a
traceback rather than the designed refusal." `subprocess.TimeoutExpired` is a
subclass of `subprocess.SubprocessError` — measured:
  $ python3 -c "import subprocess; print(issubclass(subprocess.TimeoutExpired, subprocess.SubprocessError))"
  True
and `ledger_close.py`'s module guard is
  except (OSError, subprocess.SubprocessError) as exc:
      print(f"ledger_close: could not verify -- {exc}", ...); sys.exit(2)
so a bounded timeout already produces a named refusal on stderr and exit 2,
which is the documented "could not verify" code. No traceback.

And the specific stall the commit message names, `rpc_wait_bit_killable`, is a
TASK_KILLABLE wait — killable by a fatal signal, which is the whole point of that
wait queue versus `TASK_UNINTERRUPTIBLE` — so the kill-after-timeout path does
release the case that was observed. The general case (a true D-state child) is
the reviewer's, and it stands.

All of it lives in `tools/runner/ledger_close.py`, which is PROTECTED, so it is
an owner act, not a batch. Deferred with cause; the recommended fix is to catch
`subprocess.TimeoutExpired` at the `git()` call sites and name the stall.
