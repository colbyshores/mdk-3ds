1. F1 (Low, CONFIRMED, FIXED) — THE NEW ARM READ ITS FIELDS IN A DIFFERENT BASE
--------------------------------------------------------------------------------
Quote (review-5 F1): "The new arm compares `bbox` counts with **bash arithmetic**
over fields that `decimal_measurement` now *deliberately accepts* with leading
zeros ... `$(( ))` reads `010` as octal 8 and aborts outright on `08`/`09`, while
`[ ]` ... reads the same string as decimal."

Reproduced against the shipped `canary_verdict` with `canary_stats` stubbed,
BEFORE editing anything:

    30 30 010 0 11 11   ->  rc 0  HUD VISIBLE -- 30 canary pixels ...
                                  (bbox 010,0-11,11)
    121 121 08 0 11 11  ->  rc 1  emurun.sh: line 421: 08: value too great for
                                  base (error token is "08")

The first is the worse one: the box is (11-10+1) x (11-0+1) = 24 pixels in
DECIMAL, so 30 pixels in it is exactly the contradiction the arm exists to
refuse — and it was certified green, because octal inflated the area to 48. The
second is a script death at rc 1, an undocumented exit code (this file documents
0,2,3,4,5,6,7), from a shell internal, on the line that decides a ledger row.

THE FIX IS `10#`, and that is a DECISION, not just a patch (review-5 open
question 2 asked where to close this class and left it to the builder). The
alternative — refusing leading zeros on the log-derived fields while allowing
them on `--min-frames` — would have made `decimal_measurement` two predicates
with two spellings of "is this a number", which is the exact shape batch 158
deleted a second canary-shaped copy of to close review-3 F1. One rule, one
spelling, and the arithmetic now reads a field the way every other reader in the
function already does:

    if [ $(( (10#$bx1 - 10#$bx0 + 1) * (10#$by1 - 10#$by0 + 1) )) -lt "$total" ]

Safety of the `10#`: it needs a non-empty unsigned operand, and the bbox
validation arm runs immediately above it, so all four fields are already proven
decimals in [0,399]; `bx0 <= bx1` / `by0 <= by1` are proven there too, so no
difference is negative; and the area is at most the panel's own 400 x 240 = 96000,
so it cannot overflow. Nothing about the relation changed, only the base it is
computed in.

WHAT THE FIX DOES NOT DO, stated rather than hidden: a padded line that is
CONSISTENT in decimal (`121 121 000 0 010 010`) still passes and still prints the
padded spelling on its success line. That is not a contradiction — it is the same
box, spelled differently — and the producer (`canary_stats`, which prints Python
ints) cannot emit it either way. Refusing it would be a spelling check wearing a
relation's clothes.

AND THE OCTAL READING COULD ALSO FALSE-RED, which is the half that matters for a
ledger row. `121 121 000 0 010 010` and `121 121 0 0 011 11` were both REFUSED at
the parent, because octal SHRANK the box below the count. The same defect was
ready to both pass nonsense and fail the honest.

Pins (`tests/scripts/emurun_harness_test.sh`): the premise itself (`$((010))` is
8 while `[ 010 -eq 10 ]` is true, and `$((08))` is fatal), three disagreeing
padded lines named `HUD MALFORMED`, the shell's fault string proven GONE, and two
padded-but-consistent lines proven to still pass. All six red on the parent.


2. F2 (Medium, CONFIRMED, FIXED) — THE ZERO-STRIP COST QUADRATIC TIME IN A
   CALLER-SUPPLIED FIELD
--------------------------------------------------------------------------------
Quote (review-5 F2): "The review-4 F2 fix strips leading zeros **one character per
loop iteration**, and re-runs `${v#0}` in the loop condition, so the cost is O(n²)
in the field length."

Measured on the shipped function before editing:

    len=  102     3 ms      len= 4002   779 ms
    len= 1002    60 ms      len=20002 21985 ms

`--min-frames` is the one field a CALLER spells, and it is read three times per
run (parse-time guard, `frame_floor`'s min, `frame_floor`'s last frame). A wrapper
that pads from a fixed-width or file-sourced value turned the acceptance command
into a hang instead of a verdict. That is not a curiosity and not only a
performance note: a HANG is the failure mode this entire harness exists to avoid,
which is why every other arm in the file is a NAMED refusal. A timeout and a
verdict are different things, and the file has always said so.

THE REVIEWER'S SUGGESTED FIX DOES NOT FIX IT. It recommended
`v="${v#"${v%%[!0]*}"}"` (or extglob `+(0)`). Measured, both are still quadratic —
bash's own glob backtracking has the same shape as the loop, only a smaller
constant:

    len= 3002   loop 494 ms   glob  14 ms   extglob  53 ms
    len=12002   loop  7492 ms   glob 185 ms   extglob 744 ms
    len=24002   loop 31665 ms   glob 699 ms   extglob 3434 ms   (60 002: glob 5982 ms)

What the arm needs is not the stripped STRING, it is the stripped LENGTH, and the
length arm only ever asks "does this value have no more significant digits than
the bound". That is one question about the characters BEFORE the bound's own
width: if every one of them is a zero, the significant digits fit.

    if [ "${#v}" -gt "${#2}" ]; then
        case "${v:0:${#v}-${#2}}" in *[!0]*) return 1 ;; esac
    fi
    [ "$v" -le "$2" ]

Measured on this tree: 1 ms at 102 characters, 4 ms at 20 002, 8 ms at 60 002 —
where the shipped loop took 197 s. It is also two lines shorter than what it
replaces, and it never builds a copy of a 60 KB string.

THE EQUIVALENCE IS CHECKED, NOT ASSERTED — AND AGAINST THE SHIPPED CODE, NOT A
HAND COPY. The lifted `decimal_measurement` from `git show HEAD` of the harness and
the lifted new one were run side by side over 196 field x bound pairs — 7 bounds
(0, 9, 10, 99, 399, 96000, 999999) x 28 fields including `0`, `00`, `000`, `060`,
`0000060`, `099`, `0000096001`, `9223372036854775808`, `1000`, `100000`, `999999`,
`1000000`, `399`, `400`, `0399`, `00399`, every review-3 rejection (`+121`, `-0`,
` 121`, `60x`, `x`, empty), and two 6 000-character padded fields — and the
verdicts are IDENTICAL on all 196. The reason it is exactly equivalent, not
approximately: `significant_digits(v) <= digits(max)` iff `leading_zeros(v) >=
len(v) - digits(max)` iff every one of the first `len(v) - digits(max)` characters
is a zero. And `[ ]` reads a padded operand as decimal (verified: `[ 0000060 -le
999999 ]` is true, `[ 0000096001 -le 96000 ]` is false), so the comparison never
needed the stripped string at all — which is also why the arm can pass the raw
field straight through.

This also closes review-5's open question 3 (is a >6 KB padded `--min-frames`
worth defending?): yes, and it costs nothing now, so the file does not have to
say "and we give up past 6 KB".

Pins: a 6 002-character padded field accepted, a 6 005-character padded 96001
still refused against a 96000 bound (padding smuggles nothing past a bound at
scale), a padded field whose SIGNIFICANT digits exceed the bound still refused,
and a BOUNDED-TIME row — 20 002 characters must be adjudicated inside 5 seconds.
The bound is deliberately loose on both sides: the fixed cost is 4 ms (a ~1000x
margin, so a loaded shared host cannot flake it red) and the shipped-before cost
is 22 s (a 4x margin, so it is red on the code it was written for). The row runs
the SHIPPED rule by sourcing the lifted measurement block under `timeout`, so it
is not a restated formula.
