1. WHY EVERY EARLIER CYCLE FAILED: TWO HARNESS FAULTS, NOT A WEDGED CONSOLE
-------------------------------------------------------------------------

(a) THE "WEDGE" WAS A PARKED ATM SERVICE LOOP. State seen repeatedly on
2026-11-17: ping green, :8080 accepts TCP and then sends 0 bytes, reboots
"do not help". Two `cmd reboot` sends DID take (boot_count 655 -> 657), and
:8080 still answered nothing afterwards. ONE directed discovery probe
(`atmctl.py --ip 192.168.4.167 discover`) restored a full 912-byte
status.txt immediately. That matches the discriminator of the netload_stub
troubleshooting row "service loop parked". [CORRECTED the same day: this
record first said the console ran PRE-FIX firmware. It does not. The
installed image is netload_stub/boot.firm (SHA-256 aaf5d496..., 468,480 B,
built 2026-11-09 16:00:44 -0700 from 9f3632fe047c, which was committed 14
minutes earlier). That commit already carries the socPoll(...,0) fix from
2026-11-03 (12678ff): every socPoll in the ATM loop has a 10-250 ms timeout.
And atm.log kept printing `loop alive iters=...` heartbeats, so the loop is
NOT parked. HTTP connections are accepted and then dropped, and a directed
discovery makes them succeed again. The mechanism is UNEXPLAINED, and this
is a firmware defect present in the fixed build.] status.txt already showed
it before this session made any request:
`http_requests=35 http_ok=6 http_drop=28` at 18 min uptime. AGENTS.md P10
trap 8 prescribes reboots for this state. They do not fix it. AGENTS.md is
owner-protected and was NOT edited. The owner should amend trap 8.

FIX: hw_cycle.sh sends a bounded, best-effort directed discovery (`wake`)
before every HTTP read. MDK_HW_WAKE=0 disables it (the self-test does).

(b) THE LOG READ HAD A 10 s BUDGET FOR A 725 KB FILE. mdk.log is append-only
across sessions. It had reached 724,968 B, mostly the old per-draw sample
spam. The ATM HTTP server serves ~28 KB/s with up to 40 s before the first
byte, and it ignores Range (`-r 0-99` returned 200 with 311,296 B).
Measured: full reads in 26-52 s, and a 60 s read cut off at 654,672 B. So
every 10 s `--max-time` failed, and the earlier "HTTP 200, 247,120 B body"
was a truncated read, not the whole log (its 4 markers were really 9).

FIX: hw_cycle.sh reads with MDK_HW_HTTP_TIMEOUT (default 180 s) and
`curl --fail`, so a 403/404 error body is never a baseline or a pull. The
preflight probe only asks whether the server answers (status.txt, 20 s). The
real fix bounds the file: log_3ds.cpp rotates a log over 128 KiB at boot,
mdk.log -> mdk.prev.log -> mdk.prev2.log, two generations so a timed-out
cycle's session survives the next boot too. hw_cycle.sh accepts a rotation
ONLY when the pull no longer begins with the device snapshot AND its first two
lines are the session header and `log: rotated the previous <snapshot size>-byte
log to mdk.prev.log`, and never when the baseline came from the local-copy
fallback. A pull that merely differs keeps the old baseline (review H1, below).
OWNER NOTE: AGENTS.md P10 traps 6/10 still describe mdk.log as append-only
forever; with rotation, an older session is in mdk.prev.log / mdk.prev2.log.

--------------------------------------------------

Run 6 (`make AUTOQUIT=90 PROFILE=1`). This is the wall-clock period between
frames, before the gameplay clamp, first frame excluded, with 0.1 ms

  profile: frames=2476 mean=36.340ms p50<=33.5ms p95<=67.0ms p99<=521.4ms
           max=521.437ms over16.7ms=2401 over33.3ms=1607
  profile: console model=0 family=old3ds clock=268MHz l2=none stereo=on

Reading: the loop is vsync-quantized at ~30 Hz (p50 one 33.3 ms quantum).
65% of frames miss a 30 Hz vblank (over33.3ms=1607 of 2476), and p95 is two
quanta. p99 falls in the >100 ms overflow bucket, so at least 1% of frames
(25+) stall over 100 ms, the worst at 521 ms. Stereo was ON, so both eyes
were rendered.

NOT CLAIMED: the cause of the >100 ms stalls. One candidate is the flushed
SD log writes every 60 frames (~41 points in this run, 2 lines each). That
is a hypothesis to test by A/B (one variable, three runs each per the
runbook), not a finding. This is also a frame-period capture, not a
function-level profile: it cannot populate the hot-path corpus (AGENTS.md
§2), and the VFP freeze stays as it is.
