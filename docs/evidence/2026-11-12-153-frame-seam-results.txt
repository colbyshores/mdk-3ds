§1  THE HEADLINE DEFECT: THE FRAME SEAM THREW AWAY BOTH OF ITS RESULTS
---------------------------------------------------------------------
`mdk_linux/src/render/renderer_vk.cpp`, `mdk_render_end_frame`, before this
batch, verbatim:

    flushDraws(r);
    mdk::vk::endFrame(&r->ctx);          // bool, discarded
    r->inFrame = false;
    if (!r->screenshotPath.empty()) {
        const std::string path = r->screenshotPath;
        r->screenshotPath.clear();
        captureSwapchain(r, path.c_str());
    }

`endFrame` returns false when the fence reset, the submit or the present failed.
Every one of those failures produced a frame that was reported as rendered, and
then a screenshot was read back from a swapchain image this frame never wrote and
printed its usual "[vk] screenshot: wrote …" line. That screenshot is the pinned
frame record the loop commits. A frame record that cannot be trusted is worse than
no frame record, because a frame record gets committed.

`mdk_render_begin_frame`, before this batch:

    if (!mdk::vk::beginFrame(&r->ctx, w, h, true, clear)) {
        return;                          // silent
    }

`beginFrame` returns false when the fence wait, the image acquire, the
command-buffer reset or the buffer's begin failed. Silent. This is the exact
"invisible missing picture" that the whole refusal-reporting line of work exists
for, sitting in the one function that begins every frame.

After: both results are read, both refuse through `refused()` (which remembers
each distinct request, so a device that refuses every frame costs one line and
not one per frame), and the screenshot is captured only from a frame that was
submitted. The refusal for the capture names the path it declined to write.

Why the seam prints and `vk_context.cpp` does not: the context file has no
per-request memory and a frame-boundary failure repeats every frame, so printing
there would be 60 lines a second. The seam is the layer that already owns refusal
reporting, and it is where the dedup table lives. `vk_context.cpp`'s init-path
failures are the other case: they run once per process, so they print plainly
(§2).

§4  A HAZARD FOUND WHILE READING, AND WHY IT IS FIXED THE LONG WAY ROUND
----------------------------------------------------------------------
`endFrame` resets the frame's fence and then submits with it. If the submit fails,
the fence is unsignalled and nothing will ever signal it — and `currentFrame` is
not advanced, so the NEXT `beginFrame` waits `UINT64_MAX` on that fence. One
refused submit becomes a hang two frames later. This predates the batch (the
submit-failure `return false` was already there); it is fixed here because this
batch is the change that makes the path visible.

The direct fix is `vkSignalFence`. It is not available: the vendored header this
build compiles against does not declare it —

    $ grep -c vkSignalFence mdk_linux/third_party/vulkan/include/vulkan/vulkan_core.h
    0
    $ grep -c vkGetFenceStatus mdk_linux/third_party/vulkan/include/vulkan/vulkan_core.h
    2

— so the fence is replaced instead: a fresh SIGNALED fence is created first and the
old one destroyed only if that succeeded, so a failed recovery changes nothing and
leaves the hazard printed rather than trading a hang for a null fence handle.
Third-party headers are not edited to make a call available.

§8  WHAT THIS BATCH MADE POSSIBLE, STATED RATHER THAN HIDDEN
-----------------------------------------------------------
`beginFrame` acquires the next image — which signals `presentWait` — before it
resets and begins the command buffer. Those two steps used to be unchecked, so a
successful acquire always went on to a successful return. Now either can return
false, and the signal the acquire already posted is never consumed: the next frame's
submit passes its `pWaitSemaphores` one pending signal earlier than it should. It is
a stale +1 on a counting semaphore, not a leak and not a hang; it needs a driver that
fails a reset or a begin on an otherwise healthy device; and the the `VK_ERROR_OUT_OF_DATE_KHR` retry
above can already leave the same indeterminate signal, because the spec does not say
the semaphore is untouched when an acquire fails. Nothing can be called to undo it:
Vulkan can POST a CPU semaphore signal (`vkSignalSemaphore` is declared by the
vendored header — checked, unlike `vkSignalFence`, which is not) but has no way to
WITHDRAW one. And the ordering that would avoid it, reset-and-begin BEFORE acquire,
is worse: a later acquire failure would then leave the command buffer recording, and
`vkResetCommandBuffer` on a recording buffer is invalid use, which would wedge every
frame after the first failure. Recorded as open item 3 in `docs/CONTINUATION.md`,
commented at the site, and not silently accepted.
