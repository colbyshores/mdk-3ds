1. THE SHAPE OF ALL FOUR, IN ONE LINE
--------------------------------------------------------------------------------
Batch 157 wrote a guard that asked "is this field a number?" and answered with a
character class plus a magic length. Review-3 found that the same question is asked
in four places in the same instrument and answered differently — and wrongly — in
all four:

  F1  the "not digits" arm was `*[!0-9]` with NO trailing star, so it matched only a
      field whose LAST character was a non-digit; `[ ]` parses a signed decimal, so
      `+121`, `-0`, `-500` and ` 121` walked past it.
  F2  `--min-frames` was never validated at all, 190 lines below the guard that
      exists to stop exactly that.
  F3  `bx0`/`by0` were read and printed on the SUCCESS line and compared to nothing.
  F4  each field was bounded on its own, so a line that violates the RELATIONS the
      measurement guarantees by construction was certified.

THE FIX IS ONE RULE, NOT FOUR PATCHES. `decimal_measurement <field> <max>` now
lives above the argument parser and answers "is this a decimal in [0,max]" for
every number the harness compares: the pixel counts, the rect constants, the frame
count and the caller's floor alike. The canary's private copy is deleted. A second
spelling of one rule is exactly how F1 happened: the prose, the commit message and
the test all described `*[!0-9]*` and the file shipped `*[!0-9]`.

    decimal_measurement() {
        case "$1" in ''|*[!0-9]*) return 1 ;; esac
        [ "${#1}" -le "${#2}" ] || return 1
        [ "$1" -le "$2" ]
    }

The length arm is now DERIVED from the bound instead of remembered as six: a field
with more digits than its own bound cannot be <= it, so the arm rejects nothing an
honest measurement could produce, and there is one number to keep in sync (the
bound) instead of two (the bound and a digit count).

3. F2 (Medium) — CONFIRMED: THE SAME FAIL-OPEN, 190 LINES BELOW
--------------------------------------------------------------------------------
    $ if [ 2520 -lt "" ]; then echo refused; else echo PROCEEDS; fi
    [: : integer expression expected
    PROCEEDS

`--min-frames ""` (what a wrapper passes when its own variable is unset — `set -u`
protects this script, not its caller) and `--min-frames 60x` both silently DISABLED
the short-run gate while the printed report still claimed to have measured a run.

  * `--min-frames` is now validated IN THE ARGUMENT LOOP, before anything
    expensive: a bad value is exit 2 (usage), named, and it never reaches a launch.
  * The comparison itself is now `frame_floor <last> <min>`, which checks BOTH of
    its sides and returns 5 — a refusal — when either is not a measurement, and
    returns 5 for a genuinely short run. "I cannot evaluate the floor" and "the run
    was too short" both mean "do not report"; they are printed as different
    sentences so the reason is not lost.
  * The `LAST_FRAME` reset to a safe-looking 0 is narrowed to the EMPTY case only
    (no frame line = zero frames, which is a measurement and fails any positive
    floor). A present-but-unusable value is no longer rewritten; `frame_floor` names
    it. (FRAME_RE already requires digits, so what can actually arrive is empty or
    a digit string of any length; the over-long one is what the bound catches.)
  * `MAX_FRAMES=999999` is a parseability bound, not a limit on a long run: six
    digits is ~4.6 hours of guest frames and the longest run this instrument is
    ever asked for is a two-digit `--secs`.

Rows added: 9 against the shipped `frame_floor` (including the premise row that
`[ 2520 -lt "" ]` must exit 2 — if that ever stops being true the rows above it are
decoration), plus 4 that EXECUTE the real harness with a bogus build path. The
bogus path is what makes that safe: if the parse guard were ever removed the script
falls through to its "no such build" usage error, which is also rc 2, so the row
asserts that the message names `--min-frames` — which only the guard prints — and a
paired row proves a VALID `--min-frames` is not refused.

5. F4 (Low) — CONFIRMED: THE RELATIONS THE PANEL GUARANTEES WERE NOT CHECKED
--------------------------------------------------------------------------------
    stats="96000 96000 0 0 399 239"  ->  rc 0, HUD VISIBLE   (the whole panel painted)

Every field was inside its own bound. But `canary_stats` counts `inside` as a SUBSET
of `total`, and it only counts a pixel when `cx <= CANARY_X1 and cy <= CANARY_Y1`
with both coordinates non-negative, so at most (CANARY_X1+1) x (CANARY_Y1+1) = 144
pixels can ever be inside. Both relations are now refusals, and the second bound is
DERIVED — `CANARY_MAX_INSIDE=$(( (CANARY_X1 + 1) * (CANARY_Y1 + 1) ))` — so it moves
with the rect, which the host test already re-derives from the shipped renderer.
The test reads the harness's own VALUE back out of the lifted block rather than sed-
copying the expression, and re-checks it against the renderer-derived rect.

No false-red is possible from either relation: both are guaranteed by construction,
not by measurement. The real run's 121/121 sits inside 144 with room, and the `wide`
fixture's 132 inside still reaches the containment arm and keeps its own name
(HUD OVERSIZED), which is pinned.

Rows added: 3 + 2 import/non-vacuity rows.
