2. THE SPEED PROBLEM WAS THE SIMULATION, AND IT WAS ONE FUNCTION
---------------------------------------------------------------

PROFILE builds (`AUTOQUIT=90 PROFILE=1 LEVEL=<n>`) now log where each frame
goes: the step loop, the render begin (C3D_FrameBegin's vblank wait, kept as
its own bucket), the draw issue, the end, and inside the step: Kurt, the
scripts, the camera and setSolid, with a residual.

HARDWARE, level 3: `sim=354.74ms/frame steps=10.00/frame step=35.47ms
begin(vblank wait)=8.81ms draw=7.05ms end=10.17ms`. HARDWARE, level 7 control:
`sim=8.28ms/frame steps=2.02/frame step=4.11ms begin=8.85ms draw=3.17ms
end=7.83ms`. One 60 Hz step on level 3 cost 35.5 ms, over twice its 16.7 ms
budget, so the fixed-step loop sat at its 10-step cap every frame: a death
spiral. Rendering (~26 ms) was never the problem. The same spiral reproduces in
Mandarine (EMULATOR, :99, r1.2.1 md5 0d2adab6...): step=25.50ms, of which
`player=0.03 runtime=25.46 camera=0.01 solid=0.00 residual=0.00` ms per step.
The accounting closes, and the scripts are the whole cost.

HOST, function level (callgrind, `tests/scripts/build/tick1 dump transform 3
301`, 1.46 G instructions): ScriptRuntime::poseBounds 86.5% inclusive, of which
ModelAnimation::bake 79.2% of ALL instructions, reached from the VM through
worldBounds (50.5%). Per script tick on the host: level 3 1.000 ms, level 5
1.183, level 6 0.667, level 7 0.050.

CAUSE. poseBounds baked the object's WHOLE animation (every frame, every part,
every vertex) on every call, then copied one frame out. Its own comment said
the C# caches the bake per (model, animation) and called the cache "a later
optimisation". The cache already exists in this port (scripts/pose_cache.cpp,
the C#'s MdkObject.RestPoses/Baked, dropped per level in LevelData::load) and
MdkObject::pose_parts() applies exactly poseBounds' selection (rest pose without
an animation; else the frame clamped into [0, frames-1]; else empty).

FIX. poseBounds reads `obj->pose_parts()` by reference. Same values, no bake,
no copy. This matches the oracle more closely, not less.

RESULTS.
  HOST: script tick 1.000 / 1.183 / 0.667 ms (levels 3/5/6) -> below the
    timing noise floor (|delta| < 0.05 ms over 1200 ticks).
  ORACLE: `make -C tests/scripts` (private TMPDIR) 856 PASS, rc 0, "All cases
    match the oracle." Every golden pose/transform/layout dump is unchanged.
  EMULATOR, level 3 PROFILE, same payload rebuilt: step 25.50 -> 0.37 ms,

    90 s run 330 -> 5,354, mean frame 273 -> 16.8 ms (p95 <= 20.6 ms).
  HARDWARE: NOT YET MEASURED. The console was handed to another project before
    the fixed build could run. Expected: level 3's step ~0.5 ms, so frames bound
    by render (~26 ms). That is a prediction, not a result.

NOT CLAIMED. Level 8 still OOMs (memory, Phases 1/5). Nothing here is a

3. THE LOOP, MADE SAFE TO RUN UNATTENDED ACROSS LEVELS
------------------------------------------------------

Three harness faults surfaced running six levels back to back, each now fixed
and self-tested (mdk_3ds/tools/hw_cycle_selftest.sh, 18 PASS):

- THE SD CARD FILLED. netload_stub saves a push under the file's basename, so
  mdk-L3.3dsx was a NEW 119 MB file, not an overwrite, and every later push
  ended `status=disk_full_or_io`. hw_cycle.sh now always pushes under the name
  mdk.3dsx (through a symlink); case "every push arrives as mdk.3dsx". The six
  stray copies were deleted through ATM's jailed `del`.
- A REFUSED PUSH WAS FATAL. Pushes are now retried (MDK_HW_PUSH_TRIES=12,
  MDK_HW_PUSH_GAP=10 s); case "a refused push is retried until the stub listens".
- THE STUB CAN VANISH. After a clean level-5 exit the chain-load did not
  happen: no 3dsx_app process (GDB `info os processes` on :4000), the console
  at HOME, nothing on 17491. ATM `launch` cannot start a stub it did not stage
  ("no matching staged build"); a reboot autoboots it. After 3 refusals
  (MDK_HW_REBOOT_AFTER) the harness reboots ONCE over UDP 8082 and keeps
  pushing; case "a vanished stub triggers one reboot and the push lands". Why
  the chain-load failed once (it worked after levels 3, 4, 6 and 7) is not
  known.

Also: `make -C mdk_3ds` hits an NFS race in RomFS staging ("rm: cannot remove
'build/romfs/...': Directory not empty") on about half of rebuilds; an
immediate retry passes. It is not fixed.
