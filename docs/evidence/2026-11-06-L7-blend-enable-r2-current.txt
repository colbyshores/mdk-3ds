WHY THE SUPERSEDED MD5 WAS NOT REPRODUCIBLE, measured, because the answer is a
rule and not an apology. The superseded sidecar blamed "a whitespace-only
realignment of one comment line". That is not merely unproven, it is impossible,
and the probe is cheap: appending a comment line to `render_types.h` in the
clean /tmp tree and rebuilding leaves BOTH md5s unchanged (`mdk.elf`
73bfe104…, `mdk.3dsx` 567a85a0…), and the linked ELF has no debug sections.
The real mechanism is the container. `mdk.3dsx` is ELF + SMDH + RomFS, and the
RomFS is rebuilt by `3dsxtool` walking the staged directory in readdir order:

    clean build in /tmp (ext4)  mdk.3dsx 567a85a0…   mdk.elf 73bfe104…
    clean build in the repo     mdk.3dsx 34eff8e6…   mdk.elf 73bfe104…
    (the repo tree is NFS: `ls -U build/romfs` md5 c70a72c1…, /tmp ext4:
     b798c146…, while the SORTED listing is identical, f33a5018…)

Same code, same staged files, different directory order, different .3dsx bytes.
ext4's readdir order is a hash of the names, so a /tmp build reproduces across
days and directories; an NFS one does not reproduce between staging runs at all.
So: **the .3dsx md5 is a container hash and not a build identity, and every
sidecar from now on records `mdk.elf` md5 as the code identity** (it is
reproducible across both filesystems and insensitive to comments, both measured
above). The superseded pair's `9dfed8e0` was an in-tree build, and on this tree
that number was never going to come back.
