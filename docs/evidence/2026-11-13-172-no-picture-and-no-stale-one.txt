== 2. WHAT THE FIX IS, AND WHY IT IS IN TWO PLACES ==

An exit code reports a failure; it does not un-write a destination. Two
obligations, two places:

(a) THE FRONTEND CLEARS THE DESTINATION WHEN IT COMMITS TO THE REQUEST
    (`mdk_linux/src/main.cpp`, `clearCaptureDestination`).
    Called once, after every argument refusal and before the first thing that
    can fail (renderer creation, level load, the readback, the write), so a
    failure at ANY of those points leaves no picture at the path instead of a
    stale one. This is the rule the oracle-side harness already applies to its
    own output — `tests/frames/capture_oracle.sh:171` runs `rm -f "$OUT"`
    before it runs the oracle at all — and it belongs to the frontend that made
    the request, not to whichever backend is asked to fill it.

    Only a REGULAR file is removed, decided by `stat` (which follows symlinks)
    and `S_ISREG`, then `unlink`. `std::remove` was rejected on purpose: it
    removes an empty DIRECTORY too, and `--capture=/dev/full` is how this host
    forces a write failure — a cleanup written with `std::remove` would turn a
    test lever into a way to delete a device node. A failed removal is reported
    and the run continues: the write may still succeed, and if it does not the
    exit code already says there is no picture.

(b) THE BACKEND PUBLISHES A PICTURE BY RENAME, NOT BY WRITING IN PLACE
    (`mdk_linux/src/render/renderer_vk.cpp`, `writeBmp`).
    The bytes go to a sibling `<path>.part`; only a complete write is
    `rename()`d onto the destination. A short write, a full disk or a failed
    close now leaves the destination exactly as it found it and unlinks the
    partial file this function itself created. The hazard this closes is the
    second half of the same class: a truncated BMP at the path is a file that
    EXISTS and is NON-EMPTY — which is exactly the test a capture harness
    reaches for — and the old code left one behind with only a log line.

    Side effect, measured: the reviewer's own repro now SUCCEEDS. `unlink` needs
    write permission on the DIRECTORY, not on the file, so clearing a 0444 file
    and writing a fresh one works where `fopen("wb")` failed: rc 0,
    `[vk] screenshot: wrote …`, 307254 bytes, sha 58615fc8… (the pinned frame).

`mdk_core/src/render/render.h` now states the two things this batch learned the
hard way, next to `mdk_render_capture_stats`: that `requested` counts frames the
BACKEND saw name the path (so "0 of 0 requested" can describe a run that did
ask), and that reporting a failed capture does not un-write the destination.
