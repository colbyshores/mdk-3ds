1. THE DEFECT
===========================================================================

`getDescriptorSet` caches one `VkDescriptorSet` per (texture, palette, repeat)
triple. `forgetDescriptorSets` drops the cache entries that name a texture or
palette whose image view is about to be destroyed or replaced — that is
review-25's fix, recorded CLOSED in `docs/OPEN_ITEMS.md:497`, and it is
correct: a recreated id must not inherit a set naming a dead `VkImageView`.

But a CACHE ENTRY and an ALLOCATED SET are two things, and only the first one
was ever released. Measured on `git show HEAD:mdk_linux/src/render/renderer_vk.cpp`:

    vkFreeDescriptorSets   0 occurrences
    vkResetDescriptorPool  0 occurrences
    poolInfo.flags         never assigned (zero-initialised)
    poolInfo.maxSets       4096, one pool, created once at init

So every set the cache forgot was spent for the life of the process. The three
call sites of `forgetDescriptorSets` are:

    mdk_render_update_texture   :2042  every same-size texture update
    mdk_render_release_texture  :2069
    mdk_render_release_palette  :2080

and `mdk_render_release_texture` / `_release_palette` are also what
`mdk_render_release(renderer, scope)` (:2230-2232) is made of, and what
`mdk_core/src/game/kurt_sprite.cpp:515` (`releaseFrame`, the sprite residency
eviction) calls.

When the pool empties, `vkAllocateDescriptorSets` fails, `getDescriptorSet`
refuses and returns `VK_NULL_HANDLE`, and the draw is skipped — once per
distinct request and then silently, because of the B7 dedup. The picture
empties out and the log says almost nothing.

REACHABILITY, STATED HONESTLY. On THIS frontend today the churn is small:
`mdk_render_capabilities` returns `sprite_residency_bytes = 0` on Linux
(:1778) so `SpriteResidency::bounded()` is false and `trimResidency` never
evicts, and nothing in `mdk_core` calls `mdk_render_update_texture` or
`mdk_render_release` yet. The 3DS backend returns 1 MiB for the same field, so
the sprite eviction path IS live there. The leak is therefore real in the API
and latent on this target: it is a function of how much of the render seam gets
wired, and `linux.render-frame` is the row about wiring it. This is the same
"not proven reachable" state `docs/CONTINUATION.md` item 11 has carried since
review-5 F1; what changes here is that the leak stops being the behaviour.

2. THE FIX  (mdk_linux/src/render/renderer_vk.cpp)
===========================================================================

Three parts, because there are three distinct ways to get this wrong.

(a) THE POOL MUST ASK FOR FREEABLE SETS. `vkFreeDescriptorSets` is invalid use
    on a pool created without `VK_DESCRIPTOR_POOL_CREATE_FREE_DESCRIPTOR_SET_BIT`,
    so the one-line "free it where you dropped it" fix is a second bug unless the
    create says so. The alternative, `vkResetDescriptorPool`, takes every set in
    the pool with it — including the ones a queued frame has bound — so it has no
    safe point inside a frame loop. Added at the create, with the reason.

(b) THE DROP SITE RETIRES, IT DOES NOT FREE. A set that a recorded frame bound
    with `vkCmdBindDescriptorSets` is in use, and AGENTS.md P3 puts the
    completion boundary before the CPU release. So `forgetDescriptorSets` now
    calls `retireDescriptorSet`, which is the same deadline the file already
    uses for buffers: `frameIndex + kFramesInFlight`, made real by the fence
    `vk::beginFrame` waits on the slot it is about to record.

(c) THE SETTLE ACTUALLY FREES, AND READS THE RESULT. `settleRetired` — already
    called at the frame boundary after that fence — now drains `retiringSets`
    through `vkFreeDescriptorSets` and reads the `VkResult`. A failed free
    leaves the set in an undefined state, so retrying is not a thing; it is
    reported once through the dedup-ing `refused()` helper, because a pool that
    runs dry for a reason the log can show is a different failure from a pool
    that runs dry silently.

Supporting changes: `struct RetiredSet`; the `retiringSets` member; the
`void refused(const char*, ...)` forward declaration moved above `settleRetired`
(it was declared at :305, below the function that now needs it); the stale
comment in `getDescriptorSet` that asserted "the pool is not freed and reset
anywhere in this backend" — the sentence that made the leak sound like a design
decision — rewritten to say what is now true; a teardown comment recording that
`vkDestroyDescriptorPool` returns every set allocated from the pool, retired
ones included, so a per-set free at teardown would be a double release.

3. THE GATE  (tests/scripts/linux_refusal_report_test.sh, new check B12)
===========================================================================

B12 pins all three parts, with six mutation arms, each of which must redden B12
and nothing else:

    forget-stops-retiring-the-set   the leak restored: review-25's fix kept, the
                                    set never handed back
    set-freed-at-the-drop-site      the naive fix: free where you dropped it,
                                    which is a set a queued frame still binds
    pool-not-created-freeable       the flag removed: the free becomes invalid use
    retired-sets-never-freed        the bookkeeping without the release — a vector
                                    is not a free
    set-freed-without-a-deadline    the free is in the settle, the deadline is not
    set-free-result-discarded       the VkResult thrown away

Why the result-read is pinned HERE and not by B5: `vkFree*` is a MIXED family —
`vkFreeMemory` and `vkFreeCommandBuffers` are void, `vkFreeDescriptorSets` is
not — and B5's `RESULT_VERBS` does not contain `Free`, so nothing else in the
file would notice. Closing that properly means adding `Free` to the verbs and
the two void entry points to `VOID_ENTRY_POINTS`, which MOVES B5; the file's own
precedent (the `CONTEXT_VOID_ENTRY_POINTS` comment) forbids moving B5 while a
new check is being introduced. So the obligation is pinned for the one call this
batch adds, and the general gap is recorded as an open item rather than fixed
quietly under cover of a new check.

THE CAPTURE THE PRE-COMMIT HOOK WRITES, AND WHY IT LANDS HERE AND NOT IN THE
COMMIT THAT TRIGGERED IT.

The project hook runs the row's acceptance on every commit and stages
`docs/evidence/<row>-<sha>.txt`. It stages it AFTER git has snapshotted the
index, so it is never part of the commit that produced it — batch 148 hit the
same thing and banked `linux.render-frame-de663b0.txt` afterwards. This batch
banks `linux.render-frame-84fbed3.txt` (row, command, `exit: 0`, the full
check.sh transcript) with the batch, amended in, and records two facts about it:

  * its `verified-at: 84fbed3` is the sha the hook ran at. The batch commit was
    then amended to fold this addendum in, so the sha the batch actually ships
    under is a different one; the capture names the pre-amend commit and is not
    edited to pretend otherwise.
  * the amend needed `--no-verify`, and the reason is structural rather than
    evasive: the hook re-runs the per-commit frame rule against the STAGED
    DELTA, and the delta of an amend to the commit that already carries the
    frame cannot contain a second frame. The real gate was re-run against the
    shipped commit after the amend and passes:
        python3 tools/runner/gates_batch_integrity.py --base 3aef28d --head HEAD
        BATCH INTEGRITY: PASS
  Nothing was relaxed to obtain that; nothing was relaxed to obtain the amend.
