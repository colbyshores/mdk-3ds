WHAT B12 NOW PINS, one shape per mutant, each with an arm of its own:

  (a) `retireDescriptorSet`'s body must contain `retiringSets.push_back(` — a helper that builds a

      once the pool reissues it that is a free of a LIVE set; erasing before the free loses a
      handle whose free failed.

§3. F2 (Medium) — CONFIRMED, FIXED BY THE REVIEWER'S OWN OPTION (b); THE REAL FIX IS FILED.
--------------------------------------------------------------------------------------------

The code fact is exactly as review-9 quoted it. `mdk_render_update_texture` (:2121 + :2129),
`mdk_render_release_texture` (:2147-2149) and `mdk_render_release_palette` (:2158-2160) each call
`forgetDescriptorSets(...)` and then `destroyImage(...)` in the same call, and `destroyImage`
(:1057-1062) destroys view -> image -> memory synchronously, with no deadline and no retire. So the
descriptor set waits two frames while the resource it names is freed on the spot. AGENTS.md P3
("do not overwrite, resize, or free an in-flight resource") is about the resource, not only the
handle that points at it.

This is pre-existing — `git diff` shows no `destroyImage` call site changed — and the reviewer said
so itself. What made it a finding was batch 163's comment, which said the set "waits for the same
boundary the buffers do, for the same reason", a sentence that is true of the set and reads as if it
covered the pair. Remediation is the reviewer's option (b), because option (a) is a different slice:

  * `settleRetired`'s paragraph now says THE SET, only the set, and points at the gap.
  * `retireDescriptorSet`'s doc comment carries the disclosure in full: "THE VIEW DOES NOT WAIT,
    and that is a gap rather than a design ... AGENTS.md P3 asks for the boundary on the whole
    resource, not on half of it; giving the image its own deadline is a separate slice (a
    `RetiredImage` beside this struct, settled here) and is recorded as an open item instead of
    being implied."
  * The open item is CONTINUATION item 11e.

Option (a) was NOT taken, deliberately: a `RetiredImage` changes the lifetime of every texture and
palette in the backend, interacts with `mdk_render_update_texture`'s keep-the-old-image failure
path and with teardown, and needs its own arms. Landing it beside a test-strengthening batch would
be two subsystem slices in one commit, which `ralph/builder.md` forbids.


§4. F3 (Low) — CONFIRMED, FIXED. THE COUNTS ARE DECLINED, WITH CAUSE.
---------------------------------------------------------------------

The sentence "running dry means the churn outran 4096 live sets rather than a leak" was wrong in
the direction a debugger would be led away from the cause: a retired set still occupies its slot
until `settleRetired` frees it at the frame boundary, so the budget is live PLUS pending-retired.
The comment now says so and names review-9 F3.

The optional half of the remediation — "report the two counts (`descs.size()`,
`retiringSets.size()`) in the refusal" — is DECLINED, and the reason is in the file, not in this
note: `refused()` dedups on the RENDERED SENTENCE (`renderer_vk.cpp:575-615`), and the table that
holds those sentences is capped at `kRefusalMemory = 256` with the documented behaviour "past the
cap everything prints". A volatile number inside the sentence is therefore a new key per frame, and
once 256 keys are spent it prints every frame — which is the 22500-lines-for-48-requests flood B7
exists to prevent, measured in `docs/evidence/2026-11-12-149-refusal-discovery.txt`. A diagnostic
that can only be bought by reintroducing a finding from nine reviews ago is not a cheap fix. The
same reasoning is why F4's count is printed at teardown instead (see §5).


§5. F4 (Low) — INVESTIGATED, FIXED BY THE REVIEWER'S OPTION (b).
----------------------------------------------------------------

Review-9 asked for a spec citation for "a failed free leaves it in an undefined state", and it was
right to: no such sentence is in the spec, and the vendored header
(`mdk_linux/third_party/vulkan/include/vulkan/vulkan_core.h:5213`) carries no spec prose, so there
was nothing local to cite and nothing invented either. The position now written into the comment
rests on two things that are not in dispute:

  * the result codes this call can return are OUT_OF_HOST_MEMORY / OUT_OF_DEVICE_MEMORY, and the
    spec does NOT say whether the sets were freed when it returns one;
  * its valid-usage rule is that a set "must not have been freed already".

Together those make a RETRY the unsafe branch: if the driver did take the sets, retrying is a
double free. Dropping the handle is the safe branch, and its cost is one leaked set — which is now
COUNTED (`RendererVk::lostDescriptorSets`) and printed once at teardown:

    [vk] %u descriptor set(s) were lost to failed frees and are gone from the pool for good

Teardown rather than the refusal site for the §4 reason: the count is volatile and the dedup key is
the rendered sentence. Teardown is the one place a running total cannot repeat.
