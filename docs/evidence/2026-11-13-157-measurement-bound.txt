1. F2 (Low, CONFIRMED, REPRODUCED BEFORE CHANGING ANYTHING)
================================================================================
Batch 156's F5 guard validated each stats field with a character class and reset a bad field
to a safe-looking value:

    case "$total" in ''|*[!0-9]*) total=0 ;; esac

That diagnoses "the field contains a non-digit". The defect is not about characters. It is
about a comparison that cannot be made: `[ a -lt b ]` exits 2 when it cannot parse an operand,
and an `if` cannot distinguish 2 from 1, so the arm's body is skipped and canary_verdict walks
past every rejection into `HUD VISIBLE`. A digit string past LONG_MAX is all digits:

    canary_stats -> "9223372036854775808 9223372036854775808 0 0 10 10"
    stdout: expect : HUD VISIBLE -- 9223372036854775808 canary pixels in the panel, ...
    stderr: [: 9223372036854775808: integer expression expected   (x3)
    rc 0

THE WHOLE FAMILY, measured against `git show HEAD` of the harness (i.e. batch 156, the commit
this batch replaces). Every one of these certified the ledger row green:

    "9223372036854775808 9223372036854775808 0 0 10 10"  -> rc 0
    "99999999999999999999 121 0 0 10 10"                 -> rc 0
    "121 99999999999999999999 0 0 10 10"                 -> rc 0
    "121 121 0 0 9223372036854775808 10"                 -> rc 0
    "121 121 0 0 10 99999999999999999999"                -> rc 0
    "100000 100000 0 0 10 10"                            -> rc 0   (impossible in 96000 px)
    "121 121 0 0 400 10"                                 -> rc 0   (off-panel bbox)

After the fix all seven are rc 1 (`HUD MALFORMED`), and the shipped `here` capture is still
rc 0. Vault pattern this is an instance of:
30-architecture/patterns/a-checker-that-cannot-evaluate-a-condition-must-report-err-not-false.

THE FIX.

  canary_measurement() { # <field> <max> ; 0 when it is a decimal in [0,max]
      case "$1" in ''|*[!0-9]|??????*) return 1 ;; esac
      [ "$1" -le "$2" ]
  }

The third case arm (six or more digits) is what keeps `[ "$1" -le "$2" ]` itself inside the
range the parser can read. The bounds are the panel's own geometry:

  CANARY_MAX_PIXELS=96000   # tools/panel_crop.py PANEL_SIZE: 400 columns x 240 rows
  CANARY_MAX_COORD=399      # the panel's widest axis, inclusive far index

and the host test re-derives both from panel_crop.py and reddens on disagreement, so neither
is a second spelling of a rectangle this file does not own. Nothing is silently reset to 0 or
-1 any more: an unevaluable field produces a named `HUD MALFORMED` verdict, because a value
that LOOKS safe is how the third outcome ("I could not check it") gets read as one of the
other two.

ORDERING. The counts are validated before the floor arms; the bbox is validated only just
before the extent arm that reads it. Reason: `canary_stats` prints "0 0 - - - -" when nothing
painted, which is the honest and most common failure and must keep the name `HUD NOT VISIBLE`.
Validating the bbox up front would have renamed it `HUD MALFORMED`. One row pins that.

THE OTHER SIDE OF THE SAME COMPARISON. A CANARY_MIN of `x` skips its arm exactly as an
impossible count does, so the harness now checks its own five canary constants and refuses
under its own name if one is not a measurement. This half is defensive, not reachable from the
shipped file (the constants are literals and the host test already hard-fails on a missing
one); it is there because the claim "no comparison in this function can fail to evaluate" is
only true if both sides of every one are checked.
