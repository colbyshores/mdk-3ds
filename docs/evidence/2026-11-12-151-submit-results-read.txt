1. R7-F1 (Medium) — CONFIRMED, then fixed. Three VkResults discarded.
===========================================================================
`endOneShot` was:

    vkEndCommandBuffer(cb);
    ... vkQueueSubmit(ctx->queue, 1, &submit, VK_NULL_HANDLE);
    vkQueueWaitIdle(ctx->queue);

returning void, so `createHostImage` returned true for an image whose layout
transition and buffer->image copy lived in a command stream that was never
submitted. That is review-5 F1's "an image that exists but is not the texture"
re-opened one level down, on the function batch 150 had just rewritten, and B5
could not see it because B5's regex was `r"\bvkAllocate[A-Za-z]*\s*\("` — the
gate named the verb family it had been written against instead of the property.

Fix, in this order and for a reason:
  * `endOneShot` returns bool. A failed `vkEndCommandBuffer` must NOT reach the
    submit (submitting an unfinalised command buffer is invalid use), so the
    three are sequenced, not merely checked; a refused submit skips the wait.
  * `createHostImage` reads the result. The refusal-and-destroy block that used
    to be the `else` of `if (cb)` is now `if (!uploaded)` and covers both ways
    of not uploading: no command buffer, and a command buffer whose submit was
    refused. Whoever refused it prints the cause; this line names which image
    is being destroyed instead of returned, which is the half the caller needs.
  * `captureSwapchain` fails instead of writing a BMP of a buffer nobody copied
    into (it would have printed "wrote" over the top of it).

2. The same class, found by making B5 honest instead of by looking.
===========================================================================
Widening B5 from `vkAllocate*` to the spec's result-bearing verb families
(Create/Allocate/Bind/Map/Begin/End/Queue/Device/Wait/Reset/Acquire/Enumerate/
Flush/Store/Invalidate/Release) reddened five more sites in the same file, all
of them the same defect and all fixed here:

  vkBindBufferMemory   createHostBuffer  a buffer bound to nothing, then MAPPED
                                        and handed back as a success: every
                                        memcpy landed in the CPU's copy of an
                                        unbound allocation.
  vkBindImageMemory    createHostImage   the same for an image.
  vkCreatePipelineCache mdk_render_create the handle stayed undefined and reached
                                        vkCreateGraphicsPipelines — the exact
                                        undefined-handle-into-the-next-call
                                        shape vkAllocateCommandBuffers had.
                                        A null cache is the spec's "no cache",
                                        so that is what a failure leaves.
  vkDeviceWaitIdle     mdk_render_update_mesh, outside a recorded frame: the
                                        whole point of the wait is that the
                                        previous frame may still be reading the
                                        slot; a failed wait does not establish
                                        that, so the update is now skipped
                                        rather than memcpy'd under a running
                                        frame (AGENTS.md P3's completion
                                        boundary before CPU reuse).
  vkDeviceWaitIdle     mdk_render_destroy: nothing can be done with the
                                        information except record it — the
                                        alternative to destroying is leaking —
                                        but an unfenced teardown is a fact about
                                        the run that a silent one hides.

The families are hardcoded rather than parsed out of vulkan_core.h on purpose: a
gate that stops checking when its input file is missing is a pass generator
(vault: a-gate-that-skips-on-missing-input-is-a-pass-generator). The void
families that are deliberately NOT checked are named in the comment where the
list is defined.

4. R7-F3 (Medium) — CONFIRMED, then fixed. B3 read two of three numbers.
===========================================================================
`figures = [a for a in split_args(call) if "unsigned long long" in a]` skipped
`(unsigned)mdk::vk::kFramesInFlight`, so the third number in both size-bearing
lines was derived by nothing while the check's own comment called it "the one
extra factor that belongs in a request". Reproduced: `(unsigned)8` in place of
the count passed batch 150's gate.

Figures are now keyed on any cast to an integral type and CLASSIFIED, because
the three numbers in a line are three different shapes and a per-figure rule
alone is not enough:
  * a figure built from the size            -> "size"
  * the size times the frames-in-flight    -> "total"
  * the frames-in-flight count itself      -> "frames"
  * anything else, or a rescale, or a
    literal where the count belongs        -> red
plus two set rules: the line must contain a "size" figure at all, and a "frames"
figure may not appear without the "total" it multiplies out to. That last rule
is what keeps batch 150's own arm honest — `figure-prints-frames-in-flight-only`
turns the TOTAL into a bare count, and each figure read alone would be legal.
New arm `frames-figure-replaced-by-a-literal` → B3.

5. R7-F4 (Medium) — CONFIRMED, then fixed. B4 matched one spelling.
===========================================================================
`r"\breturn[ \t]+VK_NULL_HANDLE[ \t]*;"` — so deleting the descriptor refusal and
writing `return (VK_NULL_HANDLE);`, or returning a `VK_NULL_HANDLE`-initialised
local by name, left all 12 checks green while the callers drew with the PREVIOUS
draw's descriptor set bound. Both spellings were reproduced against batch 150's
gate and both passed it, as the reviewer said.

B4 now discovers the parenthesised form and any `Vk*` local initialised to
VK_NULL_HANDLE and returned by name, and attributes the refusal per return as
before. New arms `null-return-respelled` and `null-return-through-a-named-local`
→ B4. (The named-local scan is deliberately coarse — a global name set, so it
can only ever ADD obligations, never drop them.)

6. B6 was rewritten because the shape it pinned had legitimately moved.
===========================================================================
B6 used to find the `else` sibling of `if (cb)` and look for `refused(` and
`return false` in it. Once `endOneShot` could fail, the refusal had to cover
"the submit did not run" too, and the block it moved to was one B6 could not
see. It now pins the property: the one-shot result is READ (assigned or tested),
a block that both refuses and returns false sits between that read and the
single `return true`, and there is exactly one `return true` to reach. Batch
150's arm `unfilled-image-reports-success` still reds it, and a new arm
`upload-result-discarded` — the caller stops listening to `endOneShot` — reds it
too.

results and the one unfilled-image success, and green on everything else.

Still weak, and said here rather than left implied:
  * B5 reads "the statement contains VK_SUCCESS". An assignment to a local that
    is compared somewhere else would read as unchecked, and `(void)r;` after an
    assignment would read as checked. Every checked call in the file compares in
    place, so the rule is currently the same shape as the code; it is not a
    general data-flow proof.
  * B5's families are the spec's naming convention, so a void entry point inside
    a result-bearing family (the two debug-label calls) would be flagged. Neither
    is called here; the comment names them.
  * B4's named-local scan is a file-wide name set, not a scope-aware one. It can
    only add obligations.
  * B8 pairs a call with the NEAREST PRECEDING begin, which is right for this
    file's one-begin-one-end-per-function shape and would be wrong for a function
    that began two one-shot uploads.
  * B9 is still the coarse shape batch 150 documented: last-call-in-block, not a
    proof that the freed memory is that object's.
