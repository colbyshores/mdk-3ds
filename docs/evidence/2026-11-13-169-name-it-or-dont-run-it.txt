1. THE HEADLINE FACT, AND WHY IT IS ABOUT A HARNESS AND NOT A RENDERER
-----------------------------------------------------------------------------
  Batch 168 published "levels 1..7, 300 frames each — total 0, distinct 0 on
  every one" and, as its own §"NEW, not chased", that "`--level 99` run[s] with
  the same startup draw count as level 3, which suggests an unknown level falls
  back rather than erroring".

  Neither is a measurement of levels. `optionValue()` matches `--name=value`.
  `--level` is not `--level=`. Every one of those eight runs received no level at
  all and ran the default, level 3. The evidence file records each of the seven
  as ending "exiting after 300 frames (last frame: 190 draws, 1469 triangles)" —
  the SAME draw count and the SAME triangle count seven times, which is the tell
  sitting in the table, unread.

  The real sweep, run on this batch's binary with the spelling the frontend
  actually accepts (`--level=`, 300 frames, seed 1, 320x240, `DISPLAY=:99`,
  llvapipe ICD):

    level=3  rc 0  refused 0  last frame: 190 draws, 1469 triangles
    level=4  rc 0  refused 0  last frame:  28 draws,  252 triangles
    level=5  rc 0  refused 0  last frame: 107 draws, 1682 triangles
    level=6  rc 0  refused 0  last frame:  87 draws,  926 triangles
    level=7  rc 0  refused 0  last frame: 153 draws, 1042 triangles
    level=8  rc 0  refused 0  last frame: 243 draws, 2584 triangles

  Six different scenes now produce six different draw counts, which is what a
  sweep looks like when it sweeps. Batch 168's CONCLUSION survives — zero
  refusals at every shipped level, re-established here rather than copied — but
  its METHOD did not, and one of its two open items was an artifact of the bug
  rather than a property of the frontend:

    `--level=99` does NOT fall back. It refuses: "[main] --level must be 3-8",
    rc 1. There is no silent fallback to correct the reviewer to. The open item
    is closed as "never existed", and batch 168's evidence file carries a
    CORRECTION block saying so rather than a silent rewrite.

  Why this is a harness defect and not a CLI nicety: the loop's entire method is
  "run the binary, read the number". An argument that vanishes makes the number
  describe a different run than the one being recorded, and it looks measured.

2. THE CLASS IS BIGGER THAN THAT ONE ARGUMENT, AND ALL FOUR WAYS WERE MEASURED
-----------------------------------------------------------------------------
  Before touching anything, the shipped binary (`git show HEAD` of main.cpp,
  built, run) was probed with every option value the chain reads:

    `--frames abc`            ran UNBOUNDED — killed by an 8 s watchdog
    `--frames 0`              ran UNBOUNDED — killed by an 8 s watchdog
    `--capture=p --capture-frame=abc`
                              rc 0, and NO FILE was written
    `--capture=`              rc 0, and NO FILE was written
    `--frames` (last arg)     rejected, but as "unrecognized argument: --frames"
                              — a recognised option called unrecognized
    `--level=abc`             rejected, but as "must be 3-8" about a value that
                              was never a number
    `--size=wide`, `--at=1,2` already refused. `--seed` already refused, and was
                              the only spelling that got it right.

  `atoi` answers 0 for "abc", for "0" and for "" alike, and every reader in this
  chain takes 0 to mean "no limit" or "never": `maxFrames > 0` gates the frame
  bound and `captureFrame > 0` gates the capture. So a value that failed to parse
  silently became the OPPOSITE of what was asked. A harness that asks for a
  bounded run and then never stops, and a capture harness that reports success
  with no picture, are the same defect as the invisible `--level`: the frontend
  ran something other than what it was told and said nothing.

  THE FIX IS ONE PREDICATE, NOT FOUR. `positiveCount(name, text, out)` in the
  anonymous namespace: a leading digit, `strtol`, nothing after the digits, and a
  value in [1, INT_MAX]. `--frames`, `--capture-frame` and `--level` all go
  through it; `--capture` additionally refuses an empty path; a trailing
  `--frames` says "needs a value"; an unknown argument says "unrecognized". Four
  guards asking "is this a number?" four different ways is how three of these
  survived — `--size` and `--seed` were validated, `--level` was range-checked
  (which rejects a non-number by accident, with a message about the range), and
  `--frames` and `--capture-frame` were not checked at all. This is the same
  lesson batch 158 learned one subsystem over.

  The leading-digit test is not decoration: `strtol` skips leading space and
  accepts a sign, so without it " 5", "+5" and "-5" all parse. A contract that
  says "a positive decimal number" should mean exactly that.

  AND THE HELP TEXT WAS ITSELF WRONG. The in-flight version of this fix printed
  "options take their value with an equals ... except --seed, which takes a
  separate value". `--frames` also takes a separate value. A refusal message that
  mis-states the interface it is refusing is a second bug wearing the first one's
  clothes, so it now names both.

3. THE TEST: 18 RUNTIME ARMS, AND WHY NOT ONE OF THEM IS A GREP
-----------------------------------------------------------------------------
  `tests/scripts/linux_arg_parse_test.sh`, wired into `tests/scripts/Makefile`.

  The property is "this binary, given that argument, exits non-zero and says why".
  A shape grep cannot establish that and neither can reading the source, so every
  arm runs the binary. 13 refuse arms, 2 accept arms, 1 capture arm, plus the
  two accept arms' siblings:

  * The watchdog is load-bearing, not hygiene. Four of the refuse arms make the
    PRE-fix binary run unbounded; without `timeout 60` the non-vacuity run would
    HANG instead of failing, and a hanging test is a worse instrument than a
    wrong one. rc 124 is reported as its own failure mode: "ran until the 60 s
    watchdog killed it: ... was accepted as no limit at all".
  * The refusal text is matched with `case`, never with `printf | grep -q`. A
    pipe into an early-exit consumer is a SIGPIPE race, which this loop has
    already been reviewed for twice in another harness (batches 161-162).
  * `expect_capture` asserts the FILE EXISTS AND IS NON-EMPTY, not just rc 0.
    "Did not refuse" and "did the thing asked" are different claims, and the
    refuse arms alone could be satisfied by a frontend that refuses everything.
    The two accept arms are the other half of that guard.
  * The refuse arms need neither the game data nor a display — a refusal happens
    before anything is initialised. Only the accept arms do, so a lane with no
    `MDK/` still gets 15 real arms and an explicit NOTE line naming the 3 that
    were skipped rather than quietly dropping them. A skip says so; it is not a
    pass. The whole test SKIPs only when `build-linux/mdk` does not exist.

  NON-VACUITY, run and not asserted:

    new test on WORKING sources   18 arms, 0 FAIL, rc 0
    new test on PARENT sources    18 arms, 10 FAIL, rc 1

  The ten that red on the parent are exactly the class: 3 unknown-argument rows,
  4 `--frames` rows (three of them the watchdog firing), 2 `--capture-frame`
  rows, 1 empty-`--capture` row. The eight that stay green on the parent are the
  rows that were already correct (`--size=wide`, `--level=99`, `--level=abc`,
  `--seed` x2, both accept arms, the capture arm) — they are kept precisely
  because they were already correct, so a regression in the one good spelling
  (`--seed`) is caught too.

  Collateral: the parent had no version of this test, so the four-way collapses
  to the two runs above plus the whole existing suite on the working tree, which
  is gate 1 below.
